# Ontologies & Raft study — deterministic structure, and designing for understandability

**Date:** 2026-08-12 (§4–§5 added same day) · **Subject:** `turing.ae/blog/agentic-systems-need-ontologies/` · `turing.ae/blog/raft-designing-for-understandability/` · **the full Ousterhout lecture transcript** (primary source for §4) · `raft.github.io` + the Ongaro/Ousterhout paper · the W3C SHACL Recommendation · **and a survey of Raft in production** (Kafka/KRaft, CockroachDB, TiKV, etcd/raft, MongoDB, ScyllaDB, Redpanda, HashiCorp Raft) for §5.
**Shape:** §1–§3 map the two essays onto MDLP. **§4 extracts the design *method* and checks MDLP against it — the most transferable part.** §5 tests Ousterhout's central premise against ~100 production Raft deployments.
**Status:** study document — **ungated**. Every proposal at the end flows the L-010 gate (`review-360` → `change-approver`) before touching a gated artifact.
**Provenance note:** both essays are published by **Turing Agents** — the same org whose self-evolving framework this repo runs on (CLAUDE.md). These are the systems-design foundations that framework leans on, so alignment here is not incidental; a disagreement between MDLP and these posts is worth resolving rather than noting.
**Why now:** the 2026-07-28 read-only TA audit (IX-040) found MDLP's credibility ceiling is **not** the mathematics — the math core is correct and held-out integrity genuinely holds. It is (a) **built-but-unwired constructs**, (b) **six genuine implementation bugs** in a faithful-intent implementation, and (c) toy-only evidence. Ousterhout's thesis is a direct diagnosis of (a) and (b); the ontology essay names a gate class MDLP does not have.

## 1. The one sentence this study lands on

> **Structural legality is deterministic. Competence is statistical. MDLP has formalized only the second — and pays held-out eval budget to reject candidates a free, deterministic check would have refused at the door.**

MDLP's entire gate apparatus (§2 `significant()`, §8's four clauses, §19's learned bars) answers one question: *should this be believed?* — the right question for noisy evidence. It has no mechanism that answers *is this even well-formed?* Those invariants exist — dozens of them — but they live in prose, in Python `if` statements, and in ~120 named test stubs. The audit's finding that constructs were **built but not wired** is precisely what happens when an invariant's only enforcement is a code path someone has to remember to call.

The symmetric error is worth naming too, because the ontology essay's own community makes it: using symbolic logic to decide things that are irreducibly statistical. MDLP is right that competence cannot be gated symbolically. The essay is right that structure cannot be gated statistically. **They are the two halves, not competitors.**

## 2. ONT — what the ontology essay actually argues (and its self-correction)

**Thesis:** agent loops executing probabilistic models need *deterministic external* controls. Wrap the LLM in a formal symbolic layer that mechanically vetoes outputs violating domain rules — **"the agent proposes, the ontology permits."** Probabilistic controls (prompting, evals, human review) cannot reliably prevent the failure class: *"A refund tool that fires twice moves money twice."*

**Architecture — two gates:** Gate 1 pre-tool (Pydantic: shape, types, ranges, required fields); Gate 2 post-tool (the ontology checks the *proposal*) before state changes apply. **Critical requirement: tools stay pure** — they compute and propose, never execute, until validation passes.

**The essay's own correction — and it is the most valuable thing in it.** The talk it reviews claims OWL *enforces* constraints (`owl:FunctionalProperty` for at-most-one-refund, `owl:disjointWith` for buyer≠support, `owl:oneOf` for status enums, `rdfs:domain` for referential integrity). The essay contradicts this: OWL's **open-world assumption** and **absence of a unique-name assumption** mean violations become **silent inferences, not errors** — a functional-property breach becomes a `sameAs` merge of two distinct entities; a domain violation spawns a spurious type assertion. *"The ontology is consistent. No error is raised."* — *"The guardrail accepts the bad thing and quietly rewrites your knowledge graph."*

The standard that actually validates is **SHACL**: closed-world semantics (unstated ⇒ false, not unknown), a *data graph* checked against a *shapes graph*, returning a **validation report** — `sh:conforms` plus per-result `sh:focusNode` and `sh:resultSeverity ∈ {sh:Violation, sh:Warning, sh:Info}`. Core constraint families: cardinality, value type, value range, string pattern, property pair (`sh:equals`/`sh:disjoint`/`sh:lessThan`), logical (`and`/`or`/`not`/`xone`), shape-based, node kind, and **closed shapes** (`sh:closed` — no properties beyond those declared). *(Verified against the W3C SHACL Recommendation, not taken on the essay's word.)*

### 2.1 ADOPT — O1…O6

> **⚠ O1 is revised by `STUDY-ontologies-for-mdlp.md` §2.** O1 says the slot is cut but empty. In fact **B2 Amendment A already validates union-scoped acyclicity inside `merge()`, reporting via `MergeReport.rejected`, for both grown and authored edges** — the mechanism is built and approved. The real gap is the constraint *inventory*, not the enforcement point, which makes ONT-1 cheaper and better-founded than written below. Read O1 with that correction.

**O1 — MDLP's missing gate has a slot already cut for it, and the slot is `merge()`.**
§6.2 declares `GraphStore.merge(delta: GraphDelta) -> MergeReport` **the only projection write path**, and `MergeReport` already carries `rejected: [(id, reason)]`. That is a validation-report shape, in the one place every structural write must pass through. A **structural admissibility check between EXTRACT and MERGE** requires *no architectural change* — it is a new phase inside an existing two-phase discipline, writing into an existing report field. This is an unusually clean fit and it is the single most actionable item in this study.

**O2 — the invariants to hoist are already enumerated; they are just not machine-checked against data.** A non-exhaustive shapes inventory drawn from approved text:
- prereq edges: acyclic, capped fan-in, typed `prereq` vs `part_of` with a `hard` flag (§5.1, B2 Amendment A) — *cardinality + property-pair + logical constraints*.
- a `live` node **must** carry `suite_ref` resolving to both `public` and `held_out` splits and an admitted verifier; `pending_human` nodes are excluded from `reachable`, retrieval and clustering (§1, §5.1 RC-3) — *shape-based + node-kind*.
- §17.6 `scaffold_versions`: `parents[]` cardinality **by operator** (`FIX`=1 same `component_id`; `DERIVE`≥1 new `component_id`; `CAPTURE`=0 + **required** `source_ref`); `status` machine totality (`candidate→shadow→live|retired`, no others); `revalidation` orthogonal to `status` — *cardinality + value-range + closed shapes*, today enforced only by `test_status_machine_total`.
- `agent_id` scoping: a `CAPTURE` `source_ref` naming another agent's checkpoint is refused (§17.6) — *property-pair*.
- the reserved `maintenance` suite namespace (§20.2) — *value-range on a namespace*.
- the **claims rule** (§20.6): *"every claim, lease, or in-flight marker carries a TTL or a liveness probe — no claimed-but-unexpirable state, ever."* This is stated as an invariant binding **all future additions** — exactly the kind of rule that decays into prose unless it is a shape checked over the schema. Same for the **alarm-fire rule** (*a metric read by an alarm but never written is a build failure*).

**O3 — reject-and-report, never infer. Adopt as a hard write-path rule.** The OWL failure mode has a live MDLP analog and it is not hypothetical: §6.2 MERGE applies **set-merge semantics with dedup by identity only**, so a malformed-but-hash-distinct node is *added*, not refused; and §5.1's `g.step` attributing a failure to `s*` when `coherent_with` passes is a wrong-cell absorption — the same silent `sameAs`-shaped harm RC-4 was written to prevent. **Proposed rule: no MDLP write path may resolve a structural inconsistency by inferring, merging, or coercing. It rejects and reports.** MDLP's closed-world instinct is already correct (`test_merge_never_assigns_liveness` — MERGE is a projection writer, *not a gate*); this generalizes it into a stated discipline.

**O4 — three severities, and MDLP already has homes for all three.** MDLP's structural handling is binary (admit / quarantine to `pending_human`). SHACL's severity triage maps onto existing machinery with nothing new invented: `sh:Violation` ⇒ refuse + `rejected_ingest`/`selfmod_rejected` (existing event kinds); `sh:Warning` ⇒ admit but enqueue to `pending_human` / the **B2 Amendment A `queue_rank` confirmation queue** (already approved, already built for exactly this); `sh:Info` ⇒ record only. This is a real capability upgrade at near-zero design cost.

**O5 — cost ordering: the deterministic gate must run *first*.** The essay's gate stack is cheap-then-expensive by construction. MDLP's is inverted: a structurally illegal growth candidate today consumes a `provision_suite` call, a held-out draw, and an eval run before anything notices. Under §20.4's budget tiers, that waste is charged against exactly the budget scarcity is already deferring learning for. The gate stack MDLP should state explicitly: **Gate 0 shape/type (dataclasses, already present) → Gate 1 structural admissibility (NEW, deterministic, free) → Gate 2 statistical (§8/§19, unchanged).**

**O6 — an ontology of the learning domain makes G4 specifiable.** The typed vocabulary (`Skill`, `Suite`, `Item`, `Verifier`, `DifficultyBand`, `Component`, `Checkpoint`, `WorkUnit`, `Schedule`) with declared domains and ranges gives **G4 — the representative corpus, THE credibility item** something it currently lacks: a *checkable* statement of what "representative" means. Today it is prose. With a typed skill/dependency vocabulary, corpus coverage becomes a query with an answer, and M-R's GO/NO-GO can report coverage rather than assert it.

### 2.2 AVOID — O7…O9

**O7 — do not adopt an RDF/OWL/triplestore stack.** MDLP's zero-infra identity (`pip install mdlp` runs with nothing) is load-bearing and repeatedly defended. The harvest is the **discipline** — declarative shapes, closed-world validation, report-not-inference, severities — which is implementable as a small declarative constraint table over the existing `GraphDelta`, in stdlib. Anything wanting `pyshacl`/`rdflib` is at most a full-tier optional extra, exactly the precedent set for Langfuse/ClickHouse (STUDY-automaton §5, DATA-LAYER §11).

**O8 — do not let the symbolic gate creep toward competence claims.** The failure mode on the other side of this essay is a system that "proves" a skill is mastered because the graph is consistent. The partition must be stated: the structural gate may refuse a *write*; it may never assert, raise, or discount a posterior. It is a JUDGE-side member with no path into `StateStore`.

**O9 — the essay's own lesson: don't trust a guardrail you haven't tested with a violation.** OWL *looked* like enforcement to a competent speaker. Every shape MDLP writes needs a test that feeds it a violating graph and asserts the report — the exact discipline §20.6 already imposes on alarms (*"every alarm has a test that fires it on synthetic input"*). Same rule, new surface.

## 3. RAFT — understandability as a first-class design criterion

**Thesis (Ousterhout):** understandability belongs beside correctness and efficiency as a *primary* design criterion. The rationale is operational, not aesthetic: **algorithms provide no value until implemented, and implementation always modifies them** — when implementers lack sound intuitions about the logic, the modifications are wrong. His diagnosis of Paxos is two-part: it is **opaque** (he could follow the correctness proofs without understanding *how* it worked; experts who could reliably implement it were vanishingly rare) and it is **incomplete** (single-decree Paxos solves one-time consensus; replicated logs need liveness, proposal numbering, membership change and performance grafted on with *"no agreement on any of them"*) — so **implementers extended an algorithm they didn't understand using unvetted extensions.**

Two named techniques: **problem decomposition** (leader election / normal operation / safety — minimal interaction) and **state-space minimization** (remove special cases by finding mechanisms that serve multiple purposes). Working criterion, blunt: *"try explaining both, and keep the one that explains more simply."*

**Read this against IX-040 and it is not an analogy — it is the same failure.** MDLP's spec is 650 lines, 20 sections, ~70 open parameters and ~120 named checks, with dense cross-section dependencies. A faithful-intent implementation produced built-but-unwired constructs and six genuine bugs. That is Ousterhout's predicted outcome, and understandability has never been an explicit MDLP design criterion.

### 3.1 ADOPT — R1…R7

**R1 — the safety-properties figure. Highest-value single import in this study.**
Raft states five properties that are **always true**, each tied to the mechanism maintaining it: **Election Safety** (at most one leader per term) · **Leader Append-Only** (a leader never overwrites or deletes log entries; it only appends) · **Log Matching** (if two logs contain an entry with the same index and term, the logs are identical in all entries through that index) · **Leader Completeness** (if an entry is committed in a term, it is present in the logs of all higher-term leaders) · **State Machine Safety** (if a server has applied an entry at an index, no other server ever applies a different entry at that index).

MDLP has **P1**, **P2**, and **RC-1…RC-8** — but RC-* are *root causes patched*, a changelog, not a list of things that are true. Proposed: **an MDLP safety-properties figure**, ~7 named always-true properties, each with (a) the maintaining mechanism, (b) the guarding test, (c) the owning section. Draft slate, all drawn from approved text:

| Property | Statement | Mechanism | Guard |
|---|---|---|---|
| **Measurement Independence** (P1) | No quantity that gates a decision was computed from data the optimizer could reach. | held-out split · `RedactedTruthView` · SOLVE/JUDGE wall | `test_held_out_item_ids_not_solve_readable` |
| **Judge Immutability** | No SOLVE component, in any agent, at any fleet size, has a write path into JUDGE. | §17.1 static wall + capability isolation | `test_fleet_self_modify_cannot_collectively_capture_verifier` |
| **Gate Monotonicity** | No adaptive mechanism can admit a change fixed §8 would have blocked. | §19.3 per-knob clamps at the §8 defaults | `test_each_knob_only_stricter_than_§8` |
| **Evidence Identity** | One real attempt produces exactly one posterior update; two distinct attempts never merge into one. | §6.1 occurrence hashing; StateStore keyed by consumed evidence id | `test_repeat_measurement_not_deduped`, `test_same_occurrence_deduped` |
| **Reversibility** (P2) | Every state-changing operation has an inverse reachable without data loss. | merge/prune/edge-decay · Stage-1 adapter · retained fallback · reactivation-not-deletion | `test_reactivate_restores_bytes`, `test_merge_report_shows_inverses` |
| **Provisioning** | No node in the live graph lacks a suite and an admitted verifier. | `provision_suite` + MERGE-never-assigns-liveness | `test_merge_never_assigns_liveness` |
| **Truth Canonicity** | Every non-truth store is reconstructible from truth alone, idempotently. | §6 rebuild discipline; rebuild routes through `merge()` | `test_rebuild_idempotent`, `test_rebuild_routes_through_merge` |
| **Bounded Claims** | Every claim, lease or in-flight marker carries a TTL or a liveness probe. | §6.1 work units · §20.2 schedule + supervisor lease | `test_every_claim_has_ttl_or_probe` |

Three payoffs, in order of value: **(a) it makes built-but-unwired mechanically detectable** — a property whose maintaining mechanism is not on the live path is an *unproved property*, a defect class you can audit for instead of discovering by deep-read; **(b)** it compresses 650 lines into eight statements a new implementer can hold in their head — which is the entire point; **(c)** it is the first thing a reviewer of PAPER.md will look for, and its absence is currently conspicuous.

**R2 — a state-space-minimization pass, with concrete targets.** Ousterhout's technique: find one mechanism serving multiple purposes; delete the special cases. MDLP's own **best** example of this is `significant()` — *one* primitive reused by select/commit/rollback/promote/admit (§2). That discipline was applied once and never generalized. Candidates where MDLP currently states the same mechanism twice in different vocabulary:
- **Two-stage promotion, twice.** §9 (weights: reversible adapter → base merge) and §17.3 (code: shadow/sandbox → hot-swap with retained fallback) are the same procedure — *reversible stage, then irreversible stage, with a retained fallback and a post-promotion monitor.* Candidate: **one promotion primitive parameterized by artifact kind.** Raft-style: one mechanism, two axes, no special cases.
- **Termination, twice.** §15.3 (`revisit` stop) and §16.6 (`retrieve` stop) are the same rule — *significance fails, or budget spent, or K low-gain steps.* §16.6 even says it mirrors §15.3. Candidate: an **`exhausted()` stop primitive** standing beside `significant()`. Cheap, large compression.
- **Calibration, twice.** §14 (calibrate the probability) and §19 (calibrate the thresholds) share the whole shape: learn a knob from realized outcomes, per band, off below a data floor, clamped, breaker on saturation.
- **Decay, four times.** §3 `γ_slow`/`γ_fast`, §5.1 `g.decay_edges`, §5.2 `l1_decay`, §7 discounted UCT. §7 already concedes it is *"the same γ philosophy as §3."* Naming one exponential-recency primitive with four parameterizations removes a whole class of *which-decay-applies-here* bugs — and the audit found a real bug in exactly this neighbourhood (B4 `S0` ignoring mastery).

The payoff is Ousterhout's measured one: fewer implementation defects. That is MDLP's demonstrated problem, so this is not a tidiness exercise.

**R3 — epoch discipline: never credit an artifact measured under a prior generation.** In Raft every RPC carries a **term**; a stale term is rejected mechanically and universally, and — the subtle rule — **a leader may not commit an entry from a previous term by counting replicas; it must commit an entry from its current term**, which implicitly commits the prior ones. Old evidence, however plentiful, does not count in a new epoch.

MDLP has the ingredient (`checkpoint_id` / `checkpoint_gen`) but uses it **per-site**: `invalidate()` for caches, `checkpoint_gen` for MCTS stats, `τ_cache` for the fleet projection, `revalidation=pending` + `κ_reval` for §17.6's fallback, `w_obs` for §19. Five staleness mechanisms, five vocabularies. Raft's rule generalizes them: **every record carries the checkpoint generation it was computed under; any consumer reading across generations must obtain fresh in-generation evidence or reject.**

This matters most where §17.6 is **explicitly, honestly open**: *"this narrows RC-6's stale-fallback exposure to the concurrent-check window under a tightened monitor — **it does not close it**."* The Raft rule closes it by refusing to count the old evidence at all: a reactivated fallback is not "previously validated at reduced scrutiny," it is *unvalidated in this generation*. That is a simpler rule, it removes the `κ_reval` dial, and it is state-space minimization doing exactly what it is advertised to do.

**R4 — an implementability study. Novel, cheap, and aimed straight at the credibility ceiling.** Ousterhout did not assert understandability; he **measured** it — students randomized to learn Paxos or Raft first, then quizzed: ~25% better on Raft, and roughly twice as well under regression controlling for prior Paxos exposure. (Unexpected finding worth carrying: students who learned Paxos *first* did worse on *both* tests — initial confusion propagates.)

MDLP can run the analog more cheaply than anyone, because its implementers can be agents and its conformance suite already exists: **~120 named test stubs.** Give N independent implementers (agent runs, or humans) a spec section plus its stubs; measure the conforming fraction, the unwired fraction, and where they diverge. This is (a) genuinely novel for an algorithm paper, (b) directly responsive to IX-040, and (c) MDLP practising its own thesis — measure, don't assert. Note the recursion, which is real rather than cute: **the spec is the teacher, the implementer is the learner, the stub suite is the held-out verifier.** MDLP's own §13 Tutor machinery describes this experiment.

**R5 — fleet membership change needs overlapping configurations.** Raft's membership machinery exists to prevent one failure: a cut-over where two disjoint groups each believe they hold a majority — hence **joint consensus** (entries replicate to old *and* new configurations; both must agree) or single-server-at-a-time changes, and new servers join as non-voting until caught up. §18 specifies **no membership-change procedure at all**, yet §18.2's discount `φ(k)` reads a cached projection of *who else masters k*. If the roster changes while discounts are in flight, two agents can each discount a cell believing the other covers it — a coverage hole with no error. The §5.3 `f_min` floor dominates and prevents harm (`test_coverage_floor_dominates_fleet_discount`), so this is not a safety hole — but the *coverage claim* would be silently wrong, and silently-wrong claims are the class MDLP exists to eliminate. Proposal: fleet roster as a **versioned configuration row in truth**, `φ(k)` computed against a pinned roster version, membership changed one agent at a time.

**R6 — a stated snapshot boundary before observability multiplies row volume.** Raft compacts by snapshotting applied state and discarding the log prefix, **recording the index and term of the last included entry** so the log's identity survives compaction. MDLP's rows-permanent / blobs-prunable discipline (§10, §17.6, §6.1 `w_rejected`) is stricter and correct today — but `component_invoked` fires per dispatch and §11's `trace`/`score` fire per span, so truth-row volume is about to grow with *operation*, not with *learning*. `test_rebuild_idempotent` presumes the full log. There is currently **no specified snapshot boundary**, so the first compaction anyone performs breaks rebuild determinism. Raft's answer — snapshot, and record the boundary in truth — should be specified before §11's autonomy profile ships, not after.

**R7 — completeness is a safety property, and MDLP mostly has it.** Ousterhout's charge against Paxos was as much incompleteness as opacity. §20.2's recovery predicate (four-way, *disjoint AND exhaustive*, with a **normative evaluation order**) and §17.6's total status machine are exactly right and should be named as the house standard: **every state machine in MDLP is total; every predicate is exhaustive over its domain, with an evaluation order stated when the branches could overlap.** The remaining incompleteness is the *other* kind — specified-but-unwired — which R1 makes detectable.

### 3.2 AVOID / not applicable — R8…R9

**R8 — do not import consensus.** MDLP is not a replicated state machine and has no need of leader election, quorums or log replication. §18's fleet shares a substrate through gated writes, not through agreement. The harvest is Raft's **method**, its **property-figure discipline**, and its **epoch rule** — not its protocol. (The one place the protocol's *shape* transfers is R5's membership overlap, and even there only the overlap requirement, not the joint-consensus machinery.)

**R9 — do not confuse "understandable" with "less complete."** Ousterhout's point is that Raft is *both* simpler and *more* complete than Paxos; the simplification came from state-space minimization, not from omitting cases. An R2 pass that deletes a hedge, a residual-honesty paragraph, or a failure branch has misread the source. The test is Ousterhout's: *explain both, keep the one that explains more simply* — with the same coverage.

## 4. The design method itself — from the primary source

*Added 2026-08-12 from the full lecture transcript (Ousterhout, ~60 min), which is a substantially better source for the **method** than any walkthrough of it. Timestamps cite the transcript.*

The method is stated, not implied. Ten moves:

- **M1 — Understandability is an evaluation criterion, and the argument is operational.** [01:15] *"the process of implementing an algorithm always changes it. It always has to get extended or adapted or modified in some way to fit its environment. And if the people that are implementing the algorithm can't understand it… they're not going to be able to implement it properly."* The design target is therefore not *a spec that is correct*; it is **a spec that survives being modified by someone who was not in the room.**
- **M2 — Explanation is the fitness function, and the loser is discarded.** [14:54] *"when choosing between two algorithms, we would try explaining them and we'd pick the one that was simplest to explain… if something was hard to explain, then we'd throw that one out, throw it away, see if we could find some other algorithm that was simpler to explain."* The load-bearing words are **throw it away**. You iterate on the *design*, not on the prose. Difficulty explaining is evidence about the mechanism.
- **M3 — Two techniques, named.** **Decomposition** — *"the most important thing in all of computer science"* — into pieces understandable **relatively independently, that don't interact too much**. And **state-space minimization** — *"getting rid of as many if statements as possible"* — with three sub-moves: one mechanism solving multiple problems; eliminate special cases (*"make everything fall out of the common case"*); maximize consistency and minimize non-determinism. [15:38–16:22]
- **M4 — The diagnostic signal that you have the *wrong* mechanism.** They first tried Paxos-style **ranking** of servers for elections: *"this got really complicated… we kept adding special case after special case and there were more problems and finally we hit on this idea of doing randomization and suddenly everything got really simple."* [35:19] And the confirmation they had found the right one: *"the same approach works for doing the initial timeout and that also works if we get a split vote… **The same mechanism solves both of those problems.**"* [36:06] → **Accumulating special cases means replace the mechanism, not patch it. One mechanism covering two problems means you have found it.**
- **M5 — Assume, then discharge.** *"we decided the leader log is always going to be correct. We're going to declare that the leader log is perfect."* [44:34] — which collapses open-ended reconciliation into one-way copy plus *"one if statement."* Then the obligation is paid: *"we basically made an assumption that the leader log has to be perfect and then we made sure that the leader log is in fact complete."* [53:26] Declare the invariant that makes everything simple; add the **minimum** mechanism that makes it true.
- **M6 — Over-constrain the representation on purpose.** *"we do not allow any holes in the log… the logs are always sorted in order of term. Never a higher numbered term before a lower numbered term. Not allowed."* [45:22] Illegal states made unrepresentable ⇒ whole families of cases stop existing.
- **M7 — The target is intuition, not proof.** *"the idea was to make the algorithm simple enough you could just see that it worked… your intuition that it works is natural and correct."* [49:59] The counter-example is the author himself: he read the Paxos correctness proof, *"could understand the proof enough to convince myself that the algorithm worked,"* and still could not understand the algorithm — for **years**. [13:21] **A proof is not understanding. Nor is a passing test suite, nor a passing review score.**
- **M8 — Completeness is part of the goal, not the opposite of simplicity.** [03:10] Paxos's second sin: a base algorithm plus *"a bunch of additional stuff on which there's no agreement"* — so implementers extend something they don't understand with unvetted extensions. [11:52]
- **M9 — Validate the understandability claim empirically, and engineer the fairness.** Same instructor for both lectures, matched videos and quizzes, and prior Paxos experience left in (favouring Paxos). ~25% better on Raft; ~2× under regression controlling for prior exposure; and the finding worth carrying — students who learned Paxos **first** did worse on **both** tests. [54:59–56:52]
- **M10 — Honest scope.** *"raft is still not trivial… Consensus is a hard problem, but we believe we've actually made something considerably simpler."* [16:44] Simplification is not a promise of triviality.

### 4.1 Checking MDLP against the method

**Where MDLP already does this well** — worth stating, because these are not accidents:
- **M5 assume-then-discharge, twice.** *"the SQL truth store is canonical; every other store is a rebuildable projection"* is exactly a declared authority that collapses reconciliation, discharged by §6's rebuild discipline. The **SOLVE/JUDGE partition** is the same move: declare the wall, then discharge it with a static no-write-path check plus address-space isolation.
- **M4 one-mechanism-two-problems.** `significant()` — one primitive reused by select / commit / rollback / promote / admit (§2) — is a textbook instance.
- **M6 over-constrain.** The `provision_suite` invariant makes "a live node without a suite" unrepresentable rather than checked-for, and MERGE is forbidden from ever assigning liveness.
- **M8 completeness.** §20.2's recovery predicate (*disjoint AND exhaustive*, with a **normative evaluation order**) and §17.6's total status machine meet Ousterhout's completeness bar precisely.

**Where MDLP has not applied it — four honest findings:**

**C1 — M2 has never been applied, and the spec is structurally prevented from applying it.** Every added section declares itself additive: *"no §1–§12 mechanism changes,"* *"§1–§16 mechanisms are unchanged,"* *"No change to §1–§19."* No MDLP mechanism has ever been **discarded for being hard to explain**. Additive-only is a ratchet — and MDLP knows this shape is dangerous, because **P2 says every `add` has an inverse** and **RC-4 is literally "add-only ratchet."** *MDLP applied P2 to the algorithm's data structures and not to its own specification.* That is the sharpest thing this study found, and the section headers say it themselves.

**C2 — M4's warning sign is present, and should at least be asked about per mechanism.** §20.2's recovery predicate went r2→r3→r4→r5 accumulating clauses and named special cases; §17.6 reached r7; DATA-LAYER §6.1 took 12 rounds. **An important distinction, in fairness:** most of those rounds caught *authoring* defects (claiming a field exists without writing it — the L-013 class), which is not the same as mechanism complexity, and the gate catching them is the gate working. But the *residue* is a mechanism signal: a four-way predicate with a normative evaluation order, a `κ_reval` multiplier that exists only to tighten a monitor during a window the spec admits it cannot close, a `revalidation` field held orthogonal to `status` so `status` isn't overloaded. Ousterhout's reading of that pattern is not "the author was sloppy" — it is *"we kept adding special case after special case,"* which was his cue to **replace the mechanism**. Worth asking once per mechanism; not worth assuming.

**C3 — M7: the gate scores proof-shape, never intuition-shape.** `review-360` asks *does this pass* (0–100, critical floors, blockers). Nothing asks *can someone who was not in the room explain this back correctly?* Ousterhout's own case is the warning: he could follow the proof and still not understand the algorithm. This is cheap to add and MDLP is unusually well-placed to run it (§7 RAF-7).

**C4 — additive ≠ decomposed, and MDLP conflated them.** M3's criterion is pieces understandable *relatively independently, that don't interact too much*. MDLP's layers are additive in **mechanism** — genuinely, each changes nothing below it — but not independent in **comprehension**: §20 cites §6.1, §17.1, §5.1, §5.3, §8, §19, §14, §18 and §11; §17.6 cites §10, §17.1, §17.3, §18.1, §5.1 and §12. A layer that changes no existing mechanism still adds full comprehension load if reading it requires nine other sections. **"Changes nothing below" is a safety property; it is not decomposition.** This is measurable (§7 RAF-8).

## 5. Raft in production — the natural experiment on "implementation always changes it"

M1 is a falsifiable claim. Raft has ~100+ implementations, many in production, so the claim can be checked. **It holds: every serious deployment modified Raft, and none adopted it verbatim.**

| System | Raft used for | What it changed |
|---|---|---|
| **Kafka — KRaft (KIP-595)** | metadata/control plane only; the **data plane stays ISR** | push → **pull**; index/term → offset/epoch; **no heartbeats** (leader liveness inferred from fetch timeout); divergence resolved by `LastFetchedEpoch`/`DivergingEpoch` instead of `nextIndex` decrement; an **extra commitment condition** + a "dummy leader change message"; **observers** (non-voting replicas); `quorum-state` always fsync'd; ClusterId validation; snapshots deferred to KIP-630; **no pre-vote initially** (disruptive-voter risk acknowledged and deferred) |
| **CockroachDB** | one Raft group per range (multi-raft) | batching, pipelining, **joint consensus** for atomic replication changes; found etcd/raft **deviated from the formal spec** and chose to *document the additional invariants* rather than force compliance |
| **TiKV** | multi-raft per region | batched event loop polling all groups; RocksDB `WriteBatch`; pipelining (tens of Mbps → multi-Gbps) |
| **etcd/raft** | the library much of the ecosystem builds on | **algorithm only** — the user owns storage and transport; Raft modelled as a **deterministic state machine** emitting `{Messages, LogEntries, NextState}`, explicitly so it can be tested deterministically |
| **MongoDB** | replica sets (Raft-like) | **pull-based**, independently of Kafka |
| **ScyllaDB** | topology + schema metadata | centralized topology coordinator; group0 spans all members |
| **Redpanda** | **everything** — every partition is a Raft group, **no ISR** | changes to the election process, heartbeat generation, and Kafka ACKs support |
| **HashiCorp Raft** (Consul/Nomad/Vault) | general-purpose | heartbeats processed on I/O threads — which turned out to be a bug |

**F1 — The push→pull flip happened twice independently (Kafka, MongoDB), both because the surrounding system was already a pull-based log.** The lesson is not that pull is better; it is that **the algorithm bends to the shape of the substrate it lands in, and the bend is predictable from the substrate.** MDLP's substrate is the 5-store layer inside TA. Predictable bend: §20 specifies a supervisor that *drives* cycles, but any deployment fed by an external queue will invert that into poll-driven — better to state which parts are shape-neutral than to discover the inversion in an audit.

**F2 — The deviations preserved the properties, and could be *argued about* only because the properties were named.** KIP-595's extra commitment condition — a leader may not advance the high watermark for entries from previous epochs until it has replicated one entry from its **own** epoch to a majority — exists specifically to preserve **Leader Completeness** under a pull model, and the KIP argues it explicitly against the dissertation's illustrative problem. CockroachDB, on finding etcd/raft deviating, "documented the additional invariants needed to keep the existing approach safe." **This is the empirical case for RAF-1, and it is stronger than the theoretical one:** MDLP is *already* being modified in TA, has no property list, and therefore no one — including the audit — can state what an adaptation is required to preserve. That is why IX-040 had to be a four-way deep-read instead of a checklist.

**F3 — Bugs cluster in the extensions, not the core.** Antithesis (2026) ran deterministic simulation with aggressive network-partition injection against HashiCorp Raft, Aeron Cluster, OpenRaft and MicroRaft, and found in HashiCorp Raft: **(1)** asynchronous heartbeat processing racing with main-thread state — violating **Log Matching, Leader Completeness, State Machine Safety *and* Election Safety** (four of the five); **(2)** a leadership-transfer deadlock; **(3)** a snapshot-installation livelock from not discarding logs after install. **Two of three are in extensions** — leadership transfer and `InstallSnapshot` — i.e. outside the formally verified core. Their four implicit-assumption list is a reusable implementer checklist: *each node is a synchronous process with atomic state transitions · every RPC response maps to a specific request · persistent `currentTerm`/`votedFor` stays consistent · the entire protocol including extensions is verified.* Their conclusion lands directly on M-R: *"as long as the implementations are being done by unreliable, imperfect programmers (whether humans **or LLMs**), the actual code… will only be as solid as the implementors' assumptions — not the formally verified model."* **MDLP's shape is identical**: §1–§12 core, §13–§20 extensions, and the audit found the unwired constructs and bugs in extension territory.

**F4 — Independent reimplementation is the real understandability test, and it finds what review does not.** Howard et al., *Raft Refloated* (SIGOPS OSR 2015), built a clean-slate implementation plus an event-driven simulator and an SPL formal model validating 10,000+ traces. Findings: the *"iterative protocol description"* that aids **understanding hinders implementation**, because it introduces unexpected interaction between components; the paper left *"many implementation decisions to the reader,"* especially around client-request handling; and simulation surfaced a **livelock** from the interaction of commitment conditions with client-request caching, whose fix (no-op entries) **is absent from the original specification**. Verdict: high-level ideas genuinely easier than Paxos, *"many subtleties"* at implementation level. **RAF-4's methodology is therefore prior art with a known yield — and MDLP gets the subject for free: TA *is* the independent reimplementation, and IX-040 was the first read of it. Run it as a protocol, not as an incident.**

**F5 — Deferred completeness has a price, and Kafka paid it in public — twice.** KRaft shipped without snapshots (deferred to KIP-630; the metadata log grows unbounded meanwhile) and without pre-vote (gridlock and disruptive-voter risk acknowledged, deferred). Separately, Kafka's **data** plane learned the epoch lesson the hard way: before KIP-101 it truncated using the **high watermark**, and a fast leader change could truncate a **committed** message — real data loss (KAFKA-6361). The fix was to stamp every message with a **leader epoch** and reconcile by epoch, and even that needed KIP-279 for the remaining divergence cases. **These are production receipts for RAF-3 and RAF-6:** a system that reconciled by watermark instead of epoch lost committed data; a system that deferred snapshots got unbounded growth. KIP-595 also supplies the *technique* RAF-3 was missing — the **"dummy leader change message"**: on taking leadership, immediately write a synthetic in-epoch record so the current-epoch commitment rule can fire without waiting for organic traffic. MDLP's analog: a reactivated §17.6 fallback runs a **synthetic in-generation eval** at reactivation rather than waiting for organic evidence.

**F6 — "Two control planes" and "one control plane" are both Ousterhout-legal; the sin is leaving it implicit.** Kafka runs Raft for metadata and ISR for data, arguing the planes have genuinely different requirements (consensus vs. failure-free ordering plus epoch fencing). Redpanda runs Raft for everything and sells the *absence* of two systems as the simplification. One decomposes (M3), the other minimizes state space (M3). **MDLP currently has three control planes with three vocabularies — JUDGE running gates, the §20 supervisor running liveness, the §18 fleet running coverage — and no statement of whether these are one mechanism or three.** That statement is owed either way.

**F7 — The deterministic-core boundary is worth copying outright.** etcd/raft implements the algorithm only, hands storage and transport to the user, and models Raft as a state machine whose output is `{Messages, LogEntries, NextState}` — chosen explicitly because *"in order to easily test the Raft library, its behavior should be deterministic."* MDLP's ports-and-adapters has the same instinct; the **determinism framing is the part MDLP never stated**. If the §6 loop were specified as a pure function `(state, evidence) → (writes, next_state)`, the whole learner becomes replayable and testable with no stores at all — which is what `test_rebuild_idempotent` is already groping toward from the other side.

**F8 — Trace validation against a named property set is now standard practice, and MDLP's substrate makes it nearly free.** Since ~April 2024 etcd-raft carries a TLA+ spec plus a trace-validation tool that checks whether real implementation traces refine the model (TLC as checker); it reproduced a previously reported linearizable-read bug. MDLP does not need TLA+. It needs the *shape*: a machine-checkable statement of the properties plus a validator that replays real traces against them — and **TruthStore is already a complete, canonical, replayable trace.** This upgrades RAF-1 from "write a table" to "write a table **and** a checker that runs over truth," which makes built-but-unwired detectable **at runtime** rather than only by deep-read audit.

## 6. The cross-cutting pattern all three sources name

**Propose → validate → apply, with the proposal inert until validation passes.**
- Ontology essay: *"Tools remain pure — computing and proposing changes without executing them until validation passes."*
- Raft: entries are appended and replicated but **not applied** until committed on a majority.
- MDLP arrived at this independently **three times**: §6.2 EXTRACT→MERGE, §17.3 shadow→hot-swap, §6.1 dispatch-intent-before-work.

Three independent derivations plus two external confirmations is well past the L-003 evidence bar. This is `patterns.md`'s **P-001**, and naming it has a concrete payoff: the audit's built-but-unwired constructs are, every one of them, a *validate* stage that was specified and then not placed on the apply path.

## 7. Proposed next steps — each gated before touching a gated artifact

Ranked by value against the M-R credibility ceiling. **Not all of these should run** — the top four carry the argument; the rest are queued, not endorsed (L-003: evidence, not momentum).

**Tier 1 — carry the argument**

- **RAF-1 — ALGORITHM §21 "Safety properties", in two parts.** *(a)* the ~8-property table of R1, each with mechanism · guard · section, plus the derived audit rule **a property whose mechanism is not on the live path is unproved**. *(b)* **a property checker that replays TruthStore** and reports violations — F8's trace validation, which MDLP gets nearly free because truth is already a complete canonical trace. Part (a) is the paper contribution; part (b) is what turns IX-040's defect class from *discovered by deep-read* into *detected at runtime*. Empirically motivated by F2: every production Raft adaptation could be argued safe **only because the properties were named.**
- **ONT-1 — structural admissibility gate (ALGORITHM + DATA-LAYER delta):** a declarative shapes table validated between §6.2's EXTRACT and MERGE, returning into the existing `MergeReport.rejected`; the reject-and-report rule (O3); three-severity triage routing to `rejected_ingest` / `pending_human`+`queue_rank` / record-only (O4); Gate 0→1→2 ordering (O5); stdlib-only, RDF stack out of scope (O7); one violating-input test per shape (O9). The clean insertion point is the reason to do this early.
- **RAF-7 — three authoring-stage devices added to the L-010 gate (framework + `skills/spec-change-gate`).** The gate improves *correctness* and never improves *legibility*; these three attack that directly, and all are cheap. **(a) Explain-it-back** (M2/M7/C3) — an agent that has **not** read the diff or the review reads the amended section cold and explains the mechanism back; divergence from intent is a finding, not a style note. **(b) A cut step** (F-G) — an explicit "remove anything that does not serve the goal" pass, because `review-360` scores correctness, completeness, risk and contradiction but nothing that opposes growth, so approved changes ratchet by construction. **(c) Weak-spot → rule** — solicit weak spots deliberately and convert each into a stated constraint, rather than discovering constraints when a review round trips over one (the L-013 defect class; B2 Amendment A's acyclicity check arriving as a late-round caught gap; the missing constraint inventory of `STUDY-ontologies-for-mdlp.md` §2). Complements ONT-3, which *derives* constraints from meta-properties, with an elicitation move that needs no theory. This is the only proposal that changes **how MDLP is authored** rather than what it says, and it is the one Ousterhout would run first.

  *Provenance for (b) and (c): Google's two-page "App Planning Guide" (AI Professional Certificate) — a beginner's app-planning workflow that contains an explicit cut step and an explicit weak-spot→rule step, both of which the L-010 gate lacks. Not a research source and deliberately not studied as one; these two devices are the whole of what it contributes. It also independently corroborates four things MDLP already holds — output-vs-goal separation (the `Δcompetence` vs `P(success)` correction), proposer≠decider, MVP-first (L-009), prove-on-one-real-task — and its "same process again and again, and the output has to follow the same rules every time" is a usable one-line **screening test for verifiability**, worth carrying into ONT-4's competency questions.*
- **RAF-4 — independent-reimplementation protocol** (new pre-registered doc, sibling to `M1-EVAL-PROTOCOL.md`): N independent implementers × spec section × the existing ~120 stubs; report conforming / unwired / divergent. **Prior art with known yield** (F4: Howard et al. found under-specification and a livelock that review had not) — and MDLP already has the subject in TA. Turn IX-040 from an incident into a repeatable measurement.

**Tier 2 — real gaps with production receipts**

- **RAF-3 — epoch discipline (§17.6/§7/§18.2 delta):** every record stamped with its checkpoint generation; cross-generation reads revalidate or reject. Closes §17.6's **admitted** stale-fallback residual and retires `κ_reval`. Receipts: KIP-101 (reconciling by watermark instead of epoch lost committed data) and KIP-595's current-epoch commitment rule — which also donates the missing technique, a **synthetic in-generation eval at reactivation** (Kafka's "dummy leader change message") so the rule fires without waiting for organic evidence.
- **RAF-6 — snapshot boundary (§6/§10 delta):** specify compaction with a recorded boundary so `test_rebuild_idempotent` survives it. Receipt: KRaft shipped without snapshots and grew its metadata log unbounded until KIP-630. Do this **before** §11's autonomy profile multiplies row volume.
- **RAF-2 — state-space-minimization pass** on the four R2 duplications (two-stage promotion · termination · calibration · decay), governed by C2's honest caveat: ask per mechanism whether accumulated clauses are authoring residue or a wrong-mechanism signal; do not assume.
- **RAF-8 — decomposition audit (C4):** measure cross-section reference density per layer; **additive ≠ decomposed.** Cheap to compute from the spec itself, and it makes M3's criterion checkable rather than rhetorical.

**Tier 3 — queued, not endorsed**

- **ONT-2 — domain ontology as G4's coverage definition** (O6): makes "representative corpus" a query rather than a claim. Feeds HANDOVER-v3 G4.
- **RAF-5 — fleet membership configuration (§18 delta):** versioned roster in truth, `φ(k)` pinned to a roster version, one agent at a time. Motivated by CockroachDB's region-failure case — sequential reconfiguration transiently placed two replicas in one failure domain.
- **RAF-9 — deterministic core boundary (F7):** specify the §6 loop as `(state, evidence) → (writes, next_state)`, per etcd/raft's `{Messages, LogEntries, NextState}`. Would make the learner replayable and testable with no stores.
- **RAF-10 — state which control-plane story MDLP tells (F6):** JUDGE, the §20 supervisor and the §18 fleet are three planes with three vocabularies; Kafka-style separation and Redpanda-style unification are both legitimate, leaving it implicit is not.
- **P-001 — patterns.md:** record *propose → validate → apply* with its three MDLP sites and two external confirmations. Framework-side; no gate needed.
