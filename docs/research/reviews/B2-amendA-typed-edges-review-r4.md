## Findings by dimension

### 1. Correctness

- **The `τ_traverse` re-admission claim is unsupported by, and likely inconsistent with, the mechanism it cites.** `BUILD-SPECS.md:222` states the floor is "evidence-based gating, not a structural override" because `confidence` is driven down *only* by the base spec's post-redirect outcome feedback (base Mechanism 3, `BUILD-SPECS.md:189`) — and `test_tau_traverse_floor` (:239) asserts "raising its confidence via renewed intervention evidence re-admits it." But base Mechanism 3's only confidence-*raising* pathway (`g.decay_edges()` renewal, `ALGORITHM-v0.2-pathway-learner.md:133`, "decays unless intervention evidence renews it") is itself gated on the **post-redirect outcome check**, which in turn requires the walk to have **traversed, confirmed, and redirected to `P` via the `P→S` edge** (`BUILD-SPECS.md:189`: "confirm... before redirecting," "did remediating `P` actually raise `ĉ[S]`"). Once `confidence(P→S) < τ_traverse`, the walk (per this amendment's own new rule, :222) **never traverses that edge again** — so it can never be re-confirmed, never redirected to, and the one stated renewal mechanism can never fire *on that edge* again. For any `P` whose **only** downstream dependent is `S` (a very common shape — a leaf prerequisite feeding one skill), this is a closed loop with no stated escape: the claim "renewed intervention evidence re-admits it" describes a capability the spec's own mechanism does not provide a path to exercise. For `P` with multiple downstream edges (`P→S`, `P→S2`, …), whether an independent remediation of `P` (triggered by `S2`'s own diagnostic walk) would also re-evaluate and renew the *specific* `P→S` edge's confidence is **never stated** — Mechanism 3's text is written edge-locally ("did remediating `P` actually raise `ĉ[S]`"), and the amendment neither broadens this to "re-evaluate all of `P`'s out-edges" nor confirms it stays edge-scoped. Either reading leaves the `P→S` edge's reversibility unresolved by the text as written, and the single-dependent case is unambiguously irreversible under the mechanism as specified. This is a genuine derivation error in a load-bearing claim, not a stylistic gap — a developer implementing `test_tau_traverse_floor`'s second clause literally has no code path to make it pass without inventing a mechanism the spec doesn't describe.
- **`gap-z`, the term the round-4 backlog-bound and expiry rules are built on, is never defined.** `BUILD-SPECS.md:228` ("eviction by lowest gap-z — evidence-ranked, never queue position"), `:243` ("gap-z eviction"), and `test_queue_bounded_under_sustained_arrival` (:241, "eviction selects the lowest gap-z (never the oldest/lowest-priority)") all use `gap-z` as if it is a settled, distinct quantity from the already-defined `priority(e→P) = z(confidence(e)|frontier) + z((θ−ĉ_mastery[P])/SE[P]|frontier)` (:225-226) — the wording ("never the oldest/lowest-priority") explicitly implies `gap-z ≠ priority`, i.e. it is meant to be only the second (mastery-gap) term, excluding the confidence term, precisely so eviction doesn't compound the confidence-ranking bias round 3 flagged. But no line anywhere states `gap-z := z((θ−ĉ_mastery[P])/SE[P] | frontier)` or any other formula. This is the same class of defect round 1 caught once already (finding 3, round 1: "`z(...)` is not a defined function at the point of use") reappearing in a new symbol. Since the entire round-4 claim that eviction avoids compounding the confidence bias (see Red-team) depends on `gap-z` excluding the confidence term, and that exclusion is never written down, **the correctness of this round's central backlog fix cannot be verified from the text as it stands.**
- **Verified correct, no regression:** the `\|frontier\| ≤ 1` fallback (:227, "ordering is skipped... a zero-variance term contributes `z = 0`") correctly closes the round-2/3 degenerate case — a single-element sample has no defined SD, and skipping ordering rather than computing `0/0` is the right fix; `test_degenerate_frontier` (:242) targets it. The floor-allocation-order fix (:228, "in priority order until `b_conf` is exhausted") is now unambiguous and matches its own test description.

### 2. Design faithfulness

- **`τ_traverse` diverges from the established "soft, never hard-exclude" convention this codebase specifically hardened against.** `ALGORITHM-v0.2-pathway-learner.md:145-146` states `reach_weight` is "SOFT — probabilistic, never a hard AND... one wrong/decayed prereq **dampens but never deletes** a skill from the frontier" — this is RC-4's own patch language (`ALGORITHM-v0.1-redteam.md:53`, "make `reachable` **soft**... instead of a hard AND"). Amendment A's `τ_traverse` (`BUILD-SPECS.md:222`) does the opposite in the sibling diagnostic-walk mechanism: below the floor, the edge is not dampened in ranking (which is what `priority(e→P)`'s `z(confidence(e))` term already does) — it is **excluded from traversal entirely**, a hard boolean gate layered on top of the already-existing soft ranking term. The amendment does not acknowledge that it is introducing a hard-exclusion mechanism into a codebase whose one directly analogous precedent (§5.2) was deliberately built to avoid exactly that pattern.
- The `priority(e→P)` formula's 1:1 additive combination, unweighted by an analog of §5.3's `λ` (`ALGORITHM-v0.2-pathway-learner.md:165`, registered in §12), remains an unacknowledged departure from the pattern it otherwise claims to follow — unchanged since round 2/3, still non-blocking (ranking-only, non-gating use), still worth a sentence.
- Everything else structurally faithful: candidate collection (no type short-circuit), acyclicity-over-union, `hard`-flag bounded tie-break all remain consistent with base B2 and §5.1/§5.4 conventions, unchanged from round 3's assessment.

### 3. Red-team resistance

- **`τ_traverse`, as specified, is a fresh instance of RC-4's root cause (add-only/hard-gate structures with no working inverse), reintroduced in the diagnostic-walk mechanism this amendment itself owns.** RC-4's finding (`ALGORITHM-v0.1-redteam.md:52`) was precisely: "`reachable` is a **hard AND** over prereqs... one spurious edge permanently removes a skill from the frontier." Its patch (`:53`) was to make dependency weighting **soft and reversible via decay + renewal**, never an exclusionary gate. `τ_traverse` (`BUILD-SPECS.md:222`) reinstates a hard AND-like exclusion at the edge level ("traversing only edges with `confidence ≥ τ_traverse`") whose reversibility depends on a renewal pathway that — per the Correctness finding above — is, for the common case of a single-dependent prereq, **provably absent from the mechanism as specified**, and for the multi-dependent case, **unresolved by ambiguity, not by design**. This is not a residual or a narrowing of an old risk; it is the same failure family (RC-1's "act on a point-in-time signal as if final" + RC-4's "hard-gate with no working inverse") reopened in a location the amendment itself introduces this round, framed as a *closure* of the base decision's advisory. Per this dimension's scoring rule ("score 0 if it reopens a known failure mode"), this is scored well below the acceptable band; it is not scored at the floor because the blast radius is narrower than RC-4's original finding (one edge, not global reachability collapse; other candidates/edges to the same skill remain reachable) and because the gate is at least evidence-triggered rather than arbitrary.
- **Compounding factor: the very consequence the base spec already flags as unavoidable (confounded outcome checks) is what would trip this new hard gate.** Base B2's own honest risk (`BUILD-SPECS.md:199`, :189) admits the post-redirect outcome check "cannot fully separate a causal gap from a confounded co-weakness" and that confirmation+feedback "reduce, but don't eliminate" misattribution. A single confounded false-negative outcome check (P mastered, S didn't improve, but only because of an unrelated confound, not because P→S isn't real) now has a *qualitatively worse* consequence than it did in base B2: previously it lowered `confidence` (affecting ranking only, per round 2/3's assessment); now, once enough such events accumulate below `τ_traverse=0.2`, it can permanently foreclose re-diagnosis of a true root cause. The amendment increases the stakes of a risk the base spec already, honestly, could not fully close.

## Strongest adversarial objection

The confirmation-budget aging mechanism (`+1 z-unit per skipped trigger`, `BUILD-SPECS.md:228`) is the amendment's answer to "how do we guarantee a persisting, real candidate eventually gets confirmed rather than being permanently outranked" — and it works by giving every skipped candidate an **unbounded, monotonically accumulating** advantage, so any fixed competitor is eventually overtaken. This round introduces a **second, structurally different scarce resource** — the `Q_max=12` occupancy cap on the candidate backlog itself, with eviction by lowest `gap-z` — to solve the adjacent problem (round 3's unbounded-arrival objection). But **the occupancy-queue eviction mechanism inherits none of the aging protection that makes the confirmation-budget queue's fairness guarantee actually hold.** A real root-gap candidate with a modest-but-genuine `gap-z` (a subtle, hard-to-detect true prerequisite weakness — exactly the kind of case B2 exists to catch) sitting in a `Q_max`-capped backlog under sustained per-trigger arrival of new, higher-`gap-z` candidates has **no mechanism that increases its own eviction-survival odds over time**: it is compared to whatever is currently in the queue, evicted if it ranks lowest, and re-enters "at the next trigger" (:228) with **no memory of having been evicted before** — no accruing bonus, no persistence-weighted floor, nothing analogous to the aging bump that makes the *other* queue's fairness claim actually true. If the sustained arrival rate of higher-`gap-z` candidates is not a rare tail case but routine (which round 3's own adversarial pass already argued is the foreseeable regime for this amendment's no-short-circuit collection design), this specific real candidate can be evicted **every single cycle, indefinitely**, never once accumulating the kind of unbounded advantage that would guarantee it eventually wins — the exact "delay vs. permanent starvation" distinction round 3 demanded be proven, reappears unproven in the *new* mechanism this round built specifically to answer round 3's objection. The amendment closes one queue's fairness gap by copying the aging idea, and opens an adjacent, structurally identical gap in the other queue by *not* copying it. None of the nine dimensions above states this in full (Completeness notes the missing test; Correctness/Red-team note the `gap-z` definitional gap and the `τ_traverse` reversibility gap) — but this is the compound, mechanism-level objection: the fairness property the amendment is proudest of (aging) was not generalized to the sibling mechanism (eviction) introduced in the very same revision to fix the very same class of problem.

## Verdict

**needs-revision**

Round 4 made genuine, verifiable progress on five of round 3's seven numbered items (frontier degeneracy, floor-allocation order, the acyclicity-mechanism name + cross-gate dependency, the confirmation-budget test coverage, and — procedurally — no longer leaving the `τ_traverse` question silent) and closed 17 of the 20 numbered items accumulated across all three prior rounds (see the cross-round table). But the way it closed the single most consequential of those items — the base decision's `τ_traverse` advisory — introduces a fresh, critical-dimension defect that this round's re-scrutiny finds to be more serious than anything it replaces: a hard, evidence-gated traversal exclusion whose stated reversibility path does not appear to exist for the common case, reopening RC-4's "hard-gate, no working inverse" root cause in a new location. Combined with an undefined load-bearing term (`gap-z`) and a still-unaddressed defaults-justification item carried silently from round 3, the score moves down, not up. Specific blocking changes required to clear 80:
