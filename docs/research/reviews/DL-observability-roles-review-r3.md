## Findings by dimension

### 1. Correctness

- The round-2 correctness defect (the "JUDGE-emitted" schema tag contradicting §11.2's SOLVE-usable `trace()`) is resolved: DATA-LAYER.md:145 now states plainly that `trace` rows "may come from either side," narrowing the earlier blanket claim to `score` rows only. Verified by direct comparison against §11.2 invariant 1a (DATA-LAYER.md:319).
- **New correctness gap, introduced by the combination of round-2 fixes (3) and (2) above: the write-path that reconciles "SOLVE can call `trace()`" with "the backing lives in the JUDGE data directory" is never stated, and a plain reading of the artifact's own other invariants suggests it may not hold.**
  - §17.1 (ALGORITHM-v0.2:457) states the wall invariant in two parts: a **static** check ("SOLVE has no write-path and no output-influence into JUDGE — checked as an import/dataflow constraint... SOLVE may not use reflection / `eval` / dynamic import") and a **runtime backstop** ("JUDGE runs in a separate address space with no SOLVE-held handle (capability isolation)").
  - A plain `trace()` method call on an object SOLVE already holds a reference to is **neither reflection, `eval`, nor dynamic import** — it is ordinary code, so it does not trip the static check's decidable-ban clause. Whether it violates the wall invariant at all therefore depends entirely on the runtime backstop: does SOLVE, in calling `trace()`, ever hold (directly or transitively) a handle capable of writing bytes into "the JUDGE data directory" (DATA-LAYER.md:145, :319)? The document never says.
  - Two readings are both structurally possible, and the artifact does not disambiguate:
    - **(a) Mediated:** the "trace-only, redacting `ObservabilityPort`" object SOLVE holds is a capability-respecting proxy — it marshals the call across a boundary to a JUDGE-owned writer process/thread, which performs the §11.4 redaction and the actual file write. This is consistent with §17.1's "no SOLVE-held handle" backstop, but the text never states it.
    - **(b) Unmediated:** the object is an ordinary in-process Python object (the natural, simplest implementation for the **embedded tier**, which this section calls "default when the profile is on," DATA-LAYER.md:325) that itself opens and appends to the JSONL file. Under this reading, SOLVE literally performs a write into what the document calls JUDGE's own data directory — the exact SOLVE→JUDGE write-path §17.1's wall invariant exists to prevent, via a mechanism (a plain method call) the static check does not catch.
  - Reading (b) is not merely a hypothetical worst case: §6.2 (DATA-LAYER.md:227) states outright that **"the embedded tier is single-process by definition"** — meaning §17.1's runtime backstop ("JUDGE runs in a separate address space") is, on its face, **not literally available at the embedded tier**, which is the very tier this section names as the default backing for the trace file (DATA-LAYER.md:325, :327). If JUDGE and SOLVE share one process and one address space at the embedded tier, "no SOLVE-held handle into JUDGE" has no OS/runtime mechanism to stand on there, and the only protection is the static analysis — which, per the paragraph above, does not obviously catch a plain `trace()` call.
  - This is a genuine, evidence-backed correctness gap, not present in this form in rounds 1–2 (round 2's finding #1 was about a *textual* tag mismatch; this is about whether the artifact's own invariants are jointly satisfiable for the design it now specifies).
- No arithmetic/formula defects found in §11 itself (unchanged from prior rounds — the section contains no inequalities of its own).

The file-surface fix here does something §6.1 never attempted: it grants SOLVE a genuine write call (`trace()`) whose target is stated to be JUDGE's own directory, and then asserts this is "the same" analysis without doing the equivalent work (a static or capability check on the *write* side, analogous to `test_solve_candidate_cannot_import_unredacted_truth` on the *read* side). Citing §6.1 as precedent for a case §6.1's own design does not contain is a design-faithfulness mismatch, not merely an honesty one (see also Calibration below).

### 3. Red-team resistance

- **Genuine, verified progress on two of the three surfaces round 2 named.** The `score()` emit-surface closure (round 2, unchanged) and the new `AnalyticsStore` query-surface closure (composition exclusion + import-ban + test, DATA-LAYER.md:95, :319, :340) together retire the load-bearing RC-2 instance round 2 flagged as the round's central defect: "gate decisions, calibration tuples" (DATA-LAYER.md:301) are no longer reachable from a `self_modify` candidate via either the port method or the store's general-purpose query interface, and — unlike round 2 — this is now backed by structural exclusion plus a named test, not prose alone.
- **A new, unaddressed instance of the same root-cause family (RC-2 — "the whole system is an optimizer aimed at [the verifier]," `ALGORITHM-v0.1-redteam.md:41`) opens on the file surface, and is arguably more serious than a pure read-oracle because it touches write integrity, not just confidentiality.** As detailed under Correctness: if the "trace-only, redacting `ObservabilityPort`" wired into the solve bundle is (or can trivially be implemented as) an in-process object performing its own file I/O — plausible, even likely, given the embedded tier is explicitly single-process (§6.2, DATA-LAYER.md:227) — then a `self_modify` (M3) candidate that edits SOLVE's own tool-wiring (the mutable surface that would naturally originate `kind=span` model-call traces, per DATA-LAYER.md:301) gains a **direct, uncontested write path into the file the document itself calls "the JUDGE data directory."** This is worse than round 2's read-oracle gap in kind: rather than merely observing gate posture, a compromised scaffold could **forge or corrupt** the observability record JUDGE and human auditors rely on (§20.7's "passive-informing contract," ALGORITHM-v0.2:635, explicitly depends on this substrate for failure delivery and audit trails) — undermining the evidentiary basis for exactly the unattended-operation trust model §20 is built on.
- **Why the static check doesn't obviously catch it:** §17.1's decidable ban covers reflection/`eval`/dynamic import; a `trace()` method call on a statically-wired, ordinary object is none of those, so admission analysis as currently specified would not flag it. §17.3's Stage-1 sandbox ("isolated subprocess, no write access outside SOLVE," ALGORITHM-v0.2:463) is scoped to *candidates under Stage-1 trial* — it says nothing about a **live, Stage-2-promoted** SOLVE component's ambient filesystem access during ordinary (non-sandboxed) operation, which is the population that actually emits real span/trace data continuously, per §11.1's consumer list.
- **Consistency with the document's own established pattern makes this a genuine first, not a pre-existing unaddressed edge case.** Every other admin-event write in the whole artifact — `dispatch`, `selfmod_rejected`, `component_invoked`, `rejected_ingest`, `work_unit_closed` — is written **exclusively by JUDGE-side code observing SOLVE**, never by SOLVE code itself holding a write handle (explicit: "`component_invoked`... JUDGE-side observation of SOLVE execution — the orchestrator runs SOLVE, so it sees every dispatch," ALGORITHM-v0.2 §17.6; "a row is appended by the §6 orchestrator... never by SOLVE code," ALGORITHM-v0.2 §17.6). `trace()` (r3's "either side" wording, DATA-LAYER.md:145) is the **first and only** admin-event write path in the document ever attributed to SOLVE-side code directly. This is a structural departure the document does not flag, analyze, or gate the way it gates every prior instance of the same general concern.
- **Severity call, per the agent's own rubric ("score 0 if it reopens a known failure mode; score based on residual attack surface otherwise"):** this does not clearly reopen the *specific* RC-2 instance round 1/2 already closed (the read-oracle via `score()`/`AnalyticsStore`); it is a *new, adjacent* instance of the same root cause, surfaced by the fix itself, and gated on an unresolved implementation ambiguity rather than a confirmed open door. That keeps it out of the 0 band, but it is squarely residual-attack-surface territory with a plausible, natural (not exotic) path to exploitation given the stated embedded-tier architecture — hence scored in the same weak band as round 2's central finding, not meaningfully better, despite two of three surfaces being genuinely fixed.

### 5. Safety / integrity

- No *existing* gate, the §14 calibration layer, or a verifier constraint is directly edited or weakened by §11 as revised (consistent with rounds 1–2).
- **The safety-relevant question this round turns on is whether the r3 file-surface fix is consistent with §17.1's wall invariant and §19.4's "JUDGE, not SOLVE" framing — the two hardest safety constructs this section claims to extend.** §19.4 (ALGORITHM-v0.2:572) states: "a `self_modify` (§17) or any fleet agent (§18) **cannot edit the gate calibration** to loosen its own gate — structurally closed, exactly as for the verifier and item generator." §11.2 invariant 1 claims to carry this "to the read side" across all three surfaces (DATA-LAYER.md:319). ## Strongest adversarial objection

Round 2's own adversarial pass ended with: "a developer implementing this section exactly as written... would ship a system where two of the three surfaces carrying gate-posture content remain fully open... and nothing in the test suite would catch it." Round 3 answers exactly that objection for two of the three surfaces — and in doing so, **manufactures a new instance of the identical compound one layer down, on the third.**

The r3 fix for the file surface makes two moves that are individually reasonable but jointly unexamined: (1) it concedes, for the first time in this document, that SOLVE-side code may directly emit an event (`trace()`) into the observability substrate — a departure from the "JUDGE-only writes, SOLVE only observed" pattern that holds for every other administrative record in the artifact; and (2) it states that the physical backing for that substrate lives in "the JUDGE data directory." Put together, and cross-checked against §17.1's wall invariant ("SOLVE has no write-path... into JUDGE," backed at runtime by "no SOLVE-held handle") and §6.2's own admission that "the embedded tier is single-process by definition" (meaning the address-space backstop has no literal home there, at exactly the tier this section calls default) — the document has, without stating it, created a plausible SOLVE→JUDGE write path through the one mechanism its static admission check cannot see: an ordinary method call to an object SOLVE already holds. **A developer implementing §11 exactly as written and passing every listed §11.5 test could ship the simplest, most natural implementation — an in-process trace object that appends directly to the JSONL file in the JUDGE data directory — and nothing in the test suite would catch it**, because every test added in r2 and r3 checks *read* exclusion (the sandbox, the import-ban, the raising `score()`) and none checks that the *write* is mediated. This is not a full reopening of the round-1/round-2 RC-2 instance (that one — the read-oracle via `score()`/`AnalyticsStore` — is genuinely closed); it is a fresh instance of the same root cause (RC-2: "the whole system is an optimizer aimed at [the verifier]"), now on the integrity side rather than the confidentiality side, introduced by the very fix that closed the prior round's central finding, and — as with rounds 1 and 2 before it — left unflagged in the text that claims to have closed it.
