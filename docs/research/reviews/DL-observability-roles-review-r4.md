## Findings by dimension

### 1. Correctness

- The r3 correctness defect (whether SOLVE's `trace()` write into "the JUDGE data directory" was mediated, and whether §17.1's runtime backstop even applies at the single-process embedded tier) is resolved by removing the call it was about. Verified: DATA-LAYER.md:319a states plainly there is "no SOLVE emit path to mediate," and no `trace()`/`score()` method appears anywhere in §11.2's Protocol definitions (DATA-LAYER.md:307-316, unchanged from r1-r3) as something the solve bundle exposes. This is a real, checkable fact about the artifact, not an assertion — confirmed by re-reading §2.1's bundle-composition paragraph (DATA-LAYER.md:95) in full.
- **A new, narrower correctness gap: §11.2 invariant 1's opening sentence asserts a capability ("observes every dispatch, tool call, and outcome from the outside") that is fully derived for two of its three nouns but not the third.** "Dispatch" is grounded — the §6.1/§17.6 mechanism (the orchestrator itself appends the `dispatch` event and later the `component_invoked` event as the caller of SOLVE, ALGORITHM-v0.2:483/506) makes this a property of who calls whom, not of SOLVE's cooperation. "Outcome" is grounded — outcomes are JUDGE's own eval-harness computation (§4, ALGORITHM-v0.2), never SOLVE-reported. **"Tool call," instantiated by §11.1's own "model-call cost/latency as `kind=span` entries" (DATA-LAYER.md:301), has no stated mechanism.** For the *store* calls that make up `retrieve()` (§16.4, ALGORITHM-v0.2:417-424), such a mechanism already exists elsewhere in this document: the `Stores` bundle itself is JUDGE-composed and "wired at `build_stores()` time, outside every SOLVE-editable surface" (DATA-LAYER.md:95) — SOLVE's mutable retrieval *config* chooses which query to issue, but the port object that actually executes it is not SOLVE's code, so instrumenting *that* object would genuinely observe "from the outside," the same way `RedactedTruthView` mediates reads. But §17.1 (ALGORITHM-v0.2:454) places "tool-wiring" itself — not just retrieval config — on the **mutable SOLVE side** ("solve-prompts, **tool-wiring**, decision heuristics, retrieval config... Everything affecting *how a task is attempted*"), and no analogous "the model-call client is a JUDGE-composed, non-swappable object" statement exists anywhere in §11, §16, or §17 for whatever executes an actual model-inference call during a SOLVE attempt. Absent that statement, "observes... tool call... from the outside" is asserted, not derived, for this one content type — the same *category* of gap (a claim broader than its supporting mechanism) that drove rounds 1–3, now much smaller in scope (one bullet in one table row, not a whole surface).

### 3. Red-team resistance

- **The round-3 central finding — a plausible SOLVE→JUDGE write path via a plain `trace()` method call, unpoliceable by §17.1's static check at the single-process embedded tier — is genuinely and structurally closed, not narrowed.** This is the strongest possible closure available: r3 asked "is condition X true, and if so how is it mediated?"; r4 makes X false by construction (there is no `trace()` call on the solve bundle to make at all, confirmed by DATA-LAYER.md:95's field list and §11.2's Protocol definitions carrying no solve-reachable emit method). `test_all_observability_rows_judge_authored` (DATA-LAYER.md:342) is a well-targeted regression test naming exactly this closure ("the r4 no-SOLVE-emission regression").
- **A new, narrower instance of the studied failure mode this whole section exists to close (`STUDY-automaton-autonomy.md` A2 — "shipped autonomy without working observability, so a stuck agent looks alive," DATA-LAYER.md:295) is possible if the model-call-span mechanism (Correctness, above) is left unbuilt as specified.** If nothing forces model-inference calls through a JUDGE-composed, SOLVE-unswappable client, a `self_modify` (M3) candidate that edits its own tool-wiring (an explicitly mutable SOLVE surface, ALGORITHM-v0.2:454) could — deliberately or as an incidental side effect of an otherwise-legitimate scaffold edit — stop routing model calls through whatever produces `kind=span` rows, and the resulting silence would be indistinguishable, at the `ObservabilityPort` layer, from "this SOLVE component makes no model calls." This is real A2-shaped territory (a coverage blind spot, not a corruption or leak vector), but its severity is bounded by a fact the document itself already establishes: the **liveness-critical** signals §20.6/§20.7 actually depend on — the process heartbeat, the loop-progress heartbeat, the last-success stamp (ALGORITHM-v0.2:630), and the last-completed-work-unit timestamp read "from Truth" (ALGORITHM-v0.2:633) — are all `work_unit_opened`/`work_unit_closed`/`dispatch`-level (§6.1/§20.2) events, which remain robustly JUDGE-observed regardless of tool-wiring, **not** span-level model-call data. So a self_modify candidate that silences its own span emission would not defeat any of §20's actual "is the system stuck" detectors — it would only degrade the cost/latency audit trail §11.1 names as a secondary consumer ("humans auditing an unattended run after the fact," DATA-LAYER.md:301). That is why this is scored as a residual, bounded gap rather than a reopening of A2 in the form that matters for §20's safety case.
- **Severity call, per the agent's own rubric** ("score 0 if it reopens a known failure mode; score based on residual attack surface otherwise"): this does not reopen RC-2 in the form rounds 1–3 found it (the read-oracle via `score()`/`AnalyticsStore`, and the write-path via `trace()`, are both genuinely closed); it is a new, narrower, lower-blast-radius instance of A2 (observability-coverage gameability at one content-type granularity), gated on whether the model-call-instrumentation mechanism is actually specified and enforced the way the `Stores` pattern is — which it currently is not. Scored in the "acceptable" band, at the low end, reflecting substantial genuine progress with one clearly-scoped residual.

## Strongest adversarial objection

The r4 retraction is the correct, well-executed answer to every question rounds 1–3 asked, and I could not find a way to reopen any of those three rounds' central findings — the retraction genuinely removes the ground they stood on rather than papering over it. The strongest remaining objection is therefore not a reopening but a **new question the retraction itself invites, which is precisely the one this review was asked to scrutinize**: *"All observability is JUDGE-authored" answers "who may write a trace row," but §11.1's own table promises a content type — per-model-call cost/latency — that requires an answer to a different question the section never asks: "how does a JUDGE-side observer, sitting outside SOLVE's execution and calling into it only at the dispatch/outcome boundary, see the individual model calls SOLVE makes in between?"* For the analogous store-retrieval case, this project already has the right answer (the `Stores` bundle is a JUDGE-composed, SOLVE-unswappable object — SOLVE picks *what* to ask, not *who answers*, DATA-LAYER.md:95/190) — but §17.1 places "tool-wiring" itself on the mutable SOLVE side (ALGORITHM-v0.2:454), and no equivalent "the model-call client is JUDGE-composed and SOLVE-unswappable" sentence exists anywhere in §11, §16, or §17. A developer implementing §11 exactly as written and passing every listed §11.5 test could ship a system where dispatch-level and outcome-level tracing is airtight (genuinely, this time) while the specific `kind=span` "model-call cost/latency" content §11.1 advertises is either (a) not actually producible without SOLVE cooperation the design never mandates, or (b) trivially silenced by a future `self_modify` candidate that edits its own tool-wiring — reproducing, at the narrowest possible scope, the exact failure mode (`STUDY-automaton-autonomy.md` A2) this section's own header cites as its reason for existing. The saving grace, and the reason this stays a narrower finding than any of rounds 1–3's, is that none of §20's actual liveness/safety-critical detectors (§20.6's three heartbeats, §20.7's failure-delivery contract) depend on span-level data at all — they are built entirely on the dispatch/outcome-level Truth rows that this round's fix does, genuinely, make airtight. The residual is real, on-topic, and worth closing before this gates — but it is an audit-fidelity gap, not a safety hole.
