## Findings by dimension

### 1. Correctness

- The three r6-era claims audited above are each verified accurate against their cited sources: §17.3's actual text (ALGORITHM-v0.2:462–465, re-read directly this round) states only "isolated subprocess, no write access outside SOLVE" — no network clause — and the current DATA-LAYER text no longer asserts §17.3 already covers network egress; it correctly frames both Stage-1 and Stage-2 guards as "supplementary" and "defense-in-depth... not the wall itself" (:319).
- The central r7 claim — "provider keys never exist in the SOLVE process, and a generic networking import that dials a model endpoint directly simply cannot authenticate" — is logically sound *given its own premises*: if credential material genuinely never enters the SOLVE process's memory/environment, no code running in that process, of any import shape, can present valid provider credentials to a remote endpoint. This is a stronger, capability-based security argument than any prior round's list-based (import-ban) argument, and I could not find a logical flaw in the argument as stated.
- **New correctness gap: the argument's soundness rests on two premises the text asserts but does not itself establish.** (a) That the JUDGE-side broker process is *itself* isolated from the SOLVE sandbox in the same way §17.1's runtime backstop isolates other JUDGE components ("a separate address space with no SOLVE-held handle," ALGORITHM-v0.2:457) — the text calls it "a JUDGE-side broker" (:319) but never states this isolation explicitly for the broker specifically, nor cites §17.1's runtime-backstop clause as covering it. If the broker runs as an ordinary, non-isolated local process/service, its own credential store becomes the new attack surface the design was meant to eliminate (a relocation of the hazard, not a removal of it). (b) That the "authenticated local channel" between the SOLVE-side proxy and the broker authenticates at a granularity finer than "this OS process" — because the entire SOLVE sandbox (Stage 1) or live SOLVE (Stage 2) runs as one process, a channel authenticated only at the process level would let *any* code inside that process — not just the sanctioned `InferenceClient` proxy object — reach the broker (see Red-team below for why this specific residual does not, on its own, break invariant 1's *metering* guarantee, only its *access-control* guarantee).
- No arithmetic/formula defects found in §11 itself (unchanged across all seven rounds — the section contains no inequalities of its own).

### 2. Design faithfulness

- The r7 fix reuses two idioms this document has already validated — the `Stores`-bundle DI pattern (§2.1) for the field, and the honest-extension/defense-in-depth hedging pattern for the Stage-1/Stage-2 guards — a faithful, non-inventive application, consistent with the document's best prior rounds.
- **A genuine, new faithfulness gap: the JUDGE-side broker is an entirely new architectural component that is never integrated into §17.1's own partition definition.** ALGORITHM-v0.2:455 enumerates the JUDGE set by name (eval harness + verifier, held-out set + generator, TeacherAdapter, commit/rollback/safety gates, two-stage promotion, breaker + calibration, `self_modify` budget enforcer, competence posterior + update path, §6 orchestrator loop) — no broker, no inference-relay component. Compare ALGORITHM-v0.2:641 (§20.8), which explicitly extends the same partition for its own new components: "The supervisor shell, scheduler, budget/tier enforcer, watchdogs, and delivery ledger are **JUDGE members** (**§17.1's wall extends to them**; SOLVE has no write-path)." DATA-LAYER §11 never uses the equivalent formula for the broker — it is called "JUDGE-side" (an informal, descriptive label) rather than declared, in the §20.8 style, to be a member the wall extends to. Since DATA-LAYER cannot itself edit ALGORITHM-v0.2.md (this document's own established scope precedent, §11.4's "Register scope note," :338), this is a structural gap the artifact could still close *within its own text* by explicitly asserting the extension (the way §20.8 did, in ALGORITHM itself, for its own new components) — it simply doesn't.
- Field-naming and DI-wiring are otherwise faithful to §2.1's established conventions; the two-bundle composition enumeration (:95) remains accurate and consistent with §6.1's P1 boundary precedent.

### 3. Red-team resistance

- **Genuine, verified, and in two of three cases unusually strong progress: all three of round 6's blocking items are closed**, two by fixes that exceed the literal remedy asked for (see ledger above). None of rounds 1–5's central findings (the `score()`/`AnalyticsStore` read-oracle, the file-write-mediation question, the tool-wiring-silencing vector, read-path stage-independence) are reopened — re-verified fresh this round.
- **A new, narrower instance of the same root-cause family (RC-2 / A2) opens on two adjacent, related paths, both gated on the undefined `InferenceClient` interface:**
  1. **Open-relay / exfiltration risk, contingent on undefined destination-pinning.** The document never states whether the broker's request schema restricts its network target to a fixed, JUDGE-configured registry of model-provider endpoints, or whether the SOLVE-side proxy (and, transitively, SOLVE-mutable retrieval config, which §17.1 already permits to decide "which queries to issue") can influence *what destination* the broker relays to. If destinations are JUDGE-pinned (the natural reading of "an inference client" as a software abstraction — call-a-named-model, not call-an-arbitrary-URL), this risk does not materialize; but the document does not say so, and the undefined `InferenceClient` interface (Correctness/Implementability above) is precisely the missing artifact that would settle the question either way. Absent that statement, a `self_modify` candidate that can shape outbound request content (already legitimate, via retrieval config) cannot be shown *not* to be able to induce the credentialed broker to relay content to an attacker-reachable destination under the guise of a normal, correctly-spanned model call — the exact "looks alive/looks legitimate but is compromised" shape of A2, reached through a different door than any prior round's finding.
  2. **Process-level (not object-level) channel authentication.** If "authenticated local channel" authenticates only "this is the sandboxed SOLVE process" rather than "this is specifically the sanctioned `InferenceClient` proxy object," then any code that happens to execute inside that one process — including a hypothetical rogue import — could dial the broker directly and be accepted as a legitimate caller. **Severity note, matching the agent's own rubric:** this does *not* break invariant 1's metering guarantee on its own, because the broker is stated to emit a span for every network call *it* makes, regardless of which in-process caller relayed the request (:319, "making the actual network call, emitting the span as it does") — so even a bypass of the intended calling convention would still be metered, unlike a bypass that reached the provider directly. The residual is narrower than it first appears: it is an *access-control* gap (who may ask the broker to act), not a *metering* gap (whether the act is observed) — a materially less severe class than what closed this round.
- **Severity call, per the rubric** ("score 0 if it reopens a known failure mode; score based on residual attack surface otherwise"): neither new gap reopens a closed finding from rounds 1–6; both are fresh, adjacent instances gated on (a) `self_modify`/M3 not yet existing (a design-time question, not a live exploit today, exactly as every prior round's residual has been), and (b) an interface-completeness question the artifact could close by stating the `InferenceClient` contract and the broker's destination-pinning policy explicitly. This keeps the score out of the 0 band and in "residual attack surface, comparable in kind to every prior round's own closed finding" territory.

### 5. Safety / integrity

- No *existing* gate, the §14 calibration layer, or a verifier constraint (`HUMAN-LEARNING-VERIFIER.md`) is weakened or edited by the r7 text — consistent with all six prior rounds; re-verified fresh.
- **The core safety argument is genuinely strengthened in kind, not just in wording:** moving from a list-based control (an import-ban, which is decidable but enumerable and hence gameable at the margins) to a capability-based control (credential custody: the SOLVE process literally cannot possess what it would need to authenticate) is a materially stronger security primitive, and the document's own framing of the import-bans as "defense-in-depth... not the wall itself" (:319) is an honest and correct characterization of the resulting layered posture.
- **This round's residual (Correctness/Red-team above) is, if real, a question about whether the *new* primitive's own foundation holds** — the broker's isolation and the channel's authentication granularity — not a hole in the policy the section states. §17.1's wall invariant (ALGORITHM-v0.2:457) and §19.4's "JUDGE, not SOLVE" clamp (ALGORITHM-v0.2:572) are both untouched; a bypass of the broker's access control (if the channel authenticates only at process granularity) would still be metered by the broker's own unconditional per-call spanning, so §20.6/§20.7's liveness-critical signals — restated unchanged this round ("Honest bound, unchanged... never on span data," :319) — remain unaffected either way.
- Scored 84: a small step down from r6's 85, reflecting that while the underlying primitive is stronger, the safety *claim* as currently worded leans on an unstated assumption (the broker's own isolation) that, if false, would matter more than any prior round's residual — this is the first round in the gate's history where the open question concerns the new mechanism's *own* trust boundary rather than a scoping/citation nuance around an existing one.

### 6. Efficiency / cost

- Unchanged in kind from rounds 1–6 (scored 85–88 throughout): cold-path, emit-and-forget for traces/scores, no O(n²) additions, admission-time/build-time checks are O(1) off the §6 hot path.
- **New, minor consideration, not previously present:** every model call now traverses an added local hop (SOLVE-side proxy → authenticated local channel → JUDGE-side broker → provider), where previously (r6 and earlier) the design implied a more direct in-process client call. For interactive components (e.g., the Tutor, §13, answering a learner in real time) this is on the *act path*, not the cold §11 observability path, and the document states no latency budget or bound for the added hop (a local IPC round-trip is typically sub-millisecond, but the artifact asserts nothing about it). This is a genuinely new efficiency consideration this round's design introduces, though small in magnitude and very unlikely to be material relative to the LLM call itself.

## Verdict

**needs-revision**

Specific blocking changes required to clear 80:

1. **State the JUDGE-side broker's own isolation guarantee explicitly**, in the same style ALGORITHM-v0.2 §20.8 used for its own new JUDGE-side components ("§17.1's wall extends to them"): either the broker runs inside the same isolated JUDGE address space §17.1 already establishes for the orchestrator (state this, and how), or it is a distinct process/service with its own stated isolation mechanism (container boundary, separate host, OS-level sandbox) — a bare "JUDGE-side" label is not sufficient given this is now the component holding the credentials the whole design is built to protect.
2. **Name the authentication mechanism for the "authenticated local channel"** (Unix-domain-socket peer-credential check, mTLS, shared token, or another named primitive) and state its granularity — does it authenticate the sanctioned `InferenceClient` proxy object specifically, or merely "this is the sandboxed SOLVE process"? If the latter, state explicitly (as this review's Red-team finding does) that this is an access-control residual, not a metering one, since the broker's per-call spanning is unconditional.
3. **Define the `InferenceClient` `Protocol`** (method signatures, parameters, return types) with the same rigor §11.2 gives `ObservabilityPort`/`AnalyticsStore`, and — as part of that definition — **state explicitly whether the broker's relay destination is a fixed, JUDGE-configured provider/model registry or can be influenced by SOLVE-side callers/config.** Add a corresponding test (e.g. `test_broker_relays_only_to_registered_providers`) mirroring `test_solve_process_holds_no_provider_credentials`.
