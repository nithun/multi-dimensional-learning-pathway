## Findings by dimension

### 1. Correctness

**Items 1–4 verified correct on independent re-derivation.** `:192`'s Port delta now reads `TruthStore.open_work_unit(agent_id, episode_id, suite_id, intent_key) -> WorkUnit{occurrence_id, attempt_idx}` — the 4-argument form, matching `:53` (canonical `Protocol`) and `:175` (lifecycle prose) exactly. The embedded-tier `seq` mechanism (`:174`, "one SQLite statement in one transaction, `INSERT … SELECT COUNT(*) …`") is sound: SQLite's single-writer locking model executes a single top-level write statement (implicitly its own transaction) atomically with respect to other connections, so two concurrent instances of this exact statement serialize — the second sees the first's committed row before computing its own `COUNT(*)`, giving gapless, race-free `seq` values. `dispatch`'s hash formula (`:174`, `id = hash("dispatch" ‖ agent_id ‖ episode_id ‖ suite_id ‖ action_fingerprint ‖ seq)`) is now stated exactly, and the stated exclusion of `checkpoint_id` is internally consistent with `dispatch`'s own schema (`:138`, which has no `checkpoint_id` field) — no dangling reference to a field the record doesn't carry, unlike the r8/r9-era hand-wave.

**Finding A (new, r10-specific) — the P1/§4.1 closure's own supporting citation does not say what the closure text claims it says.** `:182` states, as its load-bearing sentence: "**TruthStore is JUDGE-side** (ALGORITHM §17.1 places the eval harness, held-out set, and its generator in JUDGE...)." But `ALGORITHM-v0.2-pathway-learner.md:454` — the SOLVE bullet of the very partition being cited — explicitly states: "**SOLVE (mutable):** the solve-scaffold — solve-prompts, tool-wiring, decision heuristics, **retrieval config (which stores/queries, §16)**, and how the agent *reads/interprets* the shared graph & skills." `:182`'s own next clause relies on exactly this mechanism as the enforcement boundary: "SOLVE-visible retrieval reaches stores only through the §5.2/§16 retrieve path, which excludes held-out items from context by construction." The document being cited assigns **which stores and queries `retrieve` uses** to the mutable, agent-editable side of the partition, not the immutable JUDGE side — so the "retrieve path" `:182` leans on as the boundary is, per §17.1's own explicit classification, not itself a fixed boundary. This is a genuine correctness defect in this round's own new text: it draws a conclusion ("the boundary is the one the algorithm already has") from a citation that, read in full, states the opposite assignment for the specific mechanism the conclusion depends on. It is narrower than a full reopening (see Red-team, below, and the adversarial pass) because §16.5 does gate the *learned* rerank weights through §8, and `:182` is right that the eval harness/held-out-set/generator themselves are immutable JUDGE data — but the *path* by which SOLVE reaches stores at all (which is what actually determines whether a query can reach `evals.item_ids`) is the mutable part, and `:182` does not address this.

## Strongest adversarial objection

**The P1/§4.1 leak this round claims to close is reachable at Milestone 0, with no self-modification, no adversarial actor, and no fleet — by the most literal, non-hostile implementation of §16.4's own retrieval design.** `ALGORITHM-v0.2-pathway-learner.md:421` names `truth` (SQL) as one of the five retrieval-substrate modalities `retrieve()` may draw on: "**truth** (SQL) — factual / provenance (exact records, eval history, lineage) → **grounding + citations**." `DATA-LAYER.md:138` (this round's own pinned schema) gives `evals` the field `item_ids` directly alongside `skill`, `difficulty`, `split{public|held_out}`, `n_pass`, `n_total` — i.e., the exact identifiers §4.1 requires to "never enter `ctx`" live in the same row, at the same access level, as everything §16.4 explicitly intends to surface as "citations" grounding the agent's answer. Nowhere in `DATA-LAYER.md` or `ALGORITHM-v0.2-pathway-learner.md` is there a stated rule that the "truth (SQL) — eval history... → grounding + citations" retrieval mode must project away `item_ids` (or restrict itself to `split=public` rows) before the result reaches `ctx`. The only textual anchor for the exclusion is a single pseudocode comment, `# hot path; held-out items excluded from ctx` (`ALGORITHM-v0.2-pathway-learner.md:148`), attached to the whole `retrieve()` function in the abstract — not to the `truth` modality specifically, and not accompanied by any statement of *how* that exclusion is computed when the modality being queried is literally the store holding the held-out identifiers. A developer implementing §16.4's "truth" mode exactly as specified — "expose eval history as grounding/citations" — by returning `evals` rows (or a naive projection of them) for the agent's own recent attempts would surface `item_ids` for `split=held_out` rows into `ctx` on the very first episode that uses citation-grounded retrieval, with nobody having edited anything, self-modified anything, or acted in bad faith. This is a **more damaging** version of the round-9 finding than the one round 10 addresses: round 9's finding needed a `read_events` call the agent or its harness "could" make; this one needs only a correct, literal implementation of a retrieval mode the algorithm already mandates and this round's own schema already wires up (`item_ids` pinned at `:175`). None of the nine dimensions above state this specific form of the objection (they discuss the M3/self-modify-mutable-retrieval-config tension, which is real but requires `self_modify` to be live); this version requires nothing past what M0 already builds, which is why it is reserved for the adversarial pass rather than folded into a dimension score.

## Verdict

**needs-revision**

Round 10 makes genuine, independently-verified progress on four of round 9's five items: the stale Port-delta signature (`:192`) is fixed and now agrees with `:53`/`:175`; `open_work_unit`'s rejection contract is named concretely (`UnknownIntentKey`, `test_open_rejection_contract`); the `seq`-assignment mechanism is named for the embedded tier (and adequately, if less crisply, for the full tier); and `dispatch`'s hash formula is stated exactly with its deliberate divergence from the general rule explained. The fifth item — the P1/held-out-secrecy closure — is where this round falls short: its own supporting citation (ALGORITHM §17.1) does not establish what the closure text claims, no access-control primitive was added to the `TruthStore` port itself, and a more literal reading of §16.4's own retrieval design (not addressed by this round's fix at all) surfaces a Milestone-0-reachable version of the exact leak the round claims to have closed. The aggregate (76) is down slightly from round 9's 78, driven by this one item; it is not a regression on anything rounds 1–9 previously closed.

To clear 80, specifically:

1. **Reconcile `DATA-LAYER.md:182`'s "TruthStore is JUDGE-side" claim with `ALGORITHM-v0.2-pathway-learner.md:454`'s explicit placement of "retrieval config (which stores/queries, §16)" on the mutable SOLVE side.** Either (a) state that the `truth` retrieval modality (§16.4) is *not* freely SOLVE-configurable and name the immutable mechanism that keeps it so, or (b) if it genuinely is SOLVE-configurable, specify a different enforcement point (e.g., a JUDGE-side filter inside the `retrieve` implementation itself, applied regardless of which store/query SOLVE selects) and say so explicitly.
2. **Specify how the §16.4 "truth (SQL) — eval history... → grounding + citations" retrieval mode avoids surfacing `item_ids` for `split=held_out` rows** — the adversarial-pass finding above. This is the more urgent of the two P1 gaps because it requires no self-modification and is reachable at Milestone 0.
3. **Add a concrete enforcement primitive to the `TruthStore` port** (or state explicitly that none is being added and why the prose-level argument is judged sufficient) so that `test_held_out_item_ids_not_solve_readable` (`:226`) has something to assert against.
4. **Name the full-tier `seq`-increment's concrete locking primitive** (e.g., `UPDATE ... RETURNING`, `SELECT ... FOR UPDATE`, or a DB-native sequence) at the same concreteness as the embedded tier's `INSERT … SELECT COUNT(*)` and §6.2's shadow-copy/lock mechanism.
5. **(Minor, one line) Add the `UnknownIntentKey` exception to `:53`'s inline comment**, matching the contract-shape comments already present at `:54`/`:55`, so the canonical `Protocol` listing is self-sufficient without requiring a reader to also find `:175`/`:192`.
