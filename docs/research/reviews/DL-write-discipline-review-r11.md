## Findings by dimension

### 1. Correctness

**The round-10 correctness defect (an inverted citation) is genuinely fixed by retraction, not by patching around it.** `:182` no longer states "TruthStore is JUDGE-side"; it states the opposite — "truth is **legitimately SOLVE-reachable**: §16.4 names the truth store as one of `retrieve()`'s modalities... and §17.1 places *retrieval config* on the mutable SOLVE side" — which is a correct restatement of `ALGORITHM-v0.2-pathway-learner.md:421` ("**truth** (SQL) — factual/provenance... → grounding + citations") and `:454` ("retrieval config (which stores/queries, §16)" listed under **SOLVE (mutable)**). This is the first round to state the actual textual content of both cited passages accurately rather than citing one and contradicting it.

**Finding A (new, r11-specific, narrower) — the full-tier `seq` mechanism's newly-added concreteness introduces a race the text doesn't address: the counter row's own creation.** `:174`: "full tier — a per-`(agent, episode, suite)` counter row bumped atomically in the same DB transaction as the append (`UPDATE dispatch_seq SET n = n + 1 WHERE … RETURNING n`, row created at first dispatch)." An `UPDATE ... RETURNING n` statement presupposes the row already exists; "row created at first dispatch" implies an `INSERT` happens at some point, but the text names only the steady-state `UPDATE`, not an atomic *upsert* (e.g. `INSERT ... ON CONFLICT (agent_id,episode_id,suite_id) DO UPDATE SET n = dispatch_seq.n + 1 RETURNING n`) that would also make the **very first** dispatch for a brand-new `(agent, episode, suite)` key race-free under concurrent first-dispatchers. Two concurrent "first" dispatches for the same never-before-seen key could each attempt an `INSERT` and collide, or each could find no row and independently decide `n=1` before either commits — the exact class of race `test_seq_atomic_under_concurrency` (`:226`) claims to cover ("concurrent `dispatch` appends ⇒ distinct gapless `seq`... no lost update on either tier") but which, as specified, is not obviously closed for the row-creation instant specifically. This is narrower than any prior round's `seq` finding (the steady-state increment is now genuinely well-specified), but it is a fresh, real gap introduced by this round's own added precision — the more concrete a mechanism becomes, the more exposed its remaining edge case is.

**Finding B (new, r11-specific, shared with Consistency below) — the two-bundle/`RedactedTruthView` design is not shown to be constructible from the document's own `build_stores()` factory or consumable by its own `EvolutionLoop` example, both of which remain single-bundle.** `DATA-LAYER.md:130` ("`stores = build_stores(load_config("mdlp.toml"))`... returns **the** `Stores` bundle") and `:250-253` (`EvolutionLoop.__init__(self, stores: Stores, ...)` unpacking `stores.truth` directly) are unchanged since round 1 and describe exactly one `Stores` object being constructed and consumed. `:90`/`:182`'s claim that "**Two bundles exist**... wired at `build_stores()` time" is not merely unillustrated (which would be an implementability gap) — it is in **direct tension with a claim the document itself already made** in its one worked dependency-injection example ("the loop is unchanged," `:257`, is now ambiguous: unchanged *given which bundle*?). This is scored here, not as a "wrong formula" defect, but as a correctness-adjacent internal-contradiction defect: the document asserts a two-bundle architecture exists while its own only worked example of bundle construction and consumption shows one bundle, and nothing reconciles the two. See Consistency Finding B for the full treatment.

### 2. Design faithfulness

## Strongest adversarial objection

**Even granting the `RedactedTruthView`/two-bundle design is built exactly as described, the enforcement machinery this section borrows from ALGORITHM §17.1 (the static wall-invariant check + runtime capability isolation) is explicitly scoped to catch a SOLVE→JUDGE *write-path or output-influence*, never a SOLVE component's acquisition of an unredacted *read* handle — so nothing in the cited machinery is stated to prevent a future `self_modify` (§17.2) candidate from capturing (or being mis-wired to) the JUDGE-side bundle.** `ALGORITHM-v0.2-pathway-learner.md:457` states the wall check's scope precisely: "SOLVE has **no write-path and no output-influence into JUDGE** — checked as an import/dataflow constraint before any `self_modify` candidate is admitted... a candidate it cannot *prove* free of a **SOLVE→JUDGE write-path** is rejected." A `self_modify` candidate that edits, say, the retrieve-path plumbing to import or reference the JUDGE-side `Stores` bundle instead of the SOLVE-side one is not writing to JUDGE and is not influencing JUDGE's output — it is merely *reading* a capability it should never have been handed, which is precisely the failure mode the round-9/10/11 finding chain is about, and precisely the one property the cited wall-invariant does not claim to check. `DATA-LAYER.md:182` itself lists "any future `self_modify`-editable code" as one of the components that must receive the redacted bundle — correctly identifying the threat surface — but the enforcement it then cites (implicitly, by parallel to §17.1's pattern) is a write-path checker, not a read-capability checker, and no passage in either document states that the static dataflow check (or the M3 address-space isolation) also proves the *absence of a reference* to the unredacted store, as opposed to the absence of a write. This means the two-bundle fix, even if perfectly wired today, has no stated mechanism preventing a later, individually-innocuous-looking `self_modify` edit (e.g., "pass `stores` instead of `solve_stores` to this helper") from silently reopening the exact leak this round's fix set out to close — and the document's own self-modification chapter (§17) is precisely the place such a check would need to live, yet nothing there or in `DATA-LAYER.md` claims to provide it. None of the nine dimensions above state this specific objection (they discuss whether the mechanism is documented/wired *today*; this discusses whether, once wired, it is *durable* against the one class of future edit — `self_modify` — this entire document's broader context (§17) exists to gate).
