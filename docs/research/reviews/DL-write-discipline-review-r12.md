## Findings by dimension

### 1. Correctness

**The full-tier `seq` first-creation race (round-11 Finding A) is genuinely closed.** `DATA-LAYER.md:179`: "full tier — a per-`(agent, episode, suite)` counter row bumped atomically in the same DB transaction as the append — **including the first dispatch, via atomic upsert** (`INSERT … ON CONFLICT DO UPDATE SET n = dispatch_seq.n + 1 RETURNING n`), so concurrent FIRST dispatches for a brand-new key cannot race either." This is the correct, standard Postgres idiom: an `INSERT … ON CONFLICT (unique key) DO UPDATE …` is atomic under Postgres's own conflict-resolution machinery — two concurrent transactions inserting the same never-before-seen key will have one win the plain insert (`n=1`) and the other block on the row lock and then execute the `DO UPDATE` branch (`n=2`), which is exactly the race `test_first_dispatch_upsert_race` (`:231`) needs to hold.

**Minor, non-blocking precision nit on the same line.** `INSERT … ON CONFLICT DO UPDATE SET n = dispatch_seq.n + 1 RETURNING n` elides the conflict target — Postgres requires `ON CONFLICT (agent_id, episode_id, suite_id) DO UPDATE …` (a bare `ON CONFLICT DO UPDATE` with no target is a syntax error; only `DO NOTHING` can omit one). This is consistent with the document's established shorthand convention elsewhere on the same line ("`INSERT … SELECT COUNT(*) …`" for the embedded tier is equally abbreviated), so it reads as intentional prose-shorthand rather than a claimed-literal SQL string, and I do not score it as a correctness defect — but a developer building against this line needs the conflict target added. Noted for completeness, not blocking.

**Finding A (new, r12-specific, narrow) — `RedactedTruthView`'s class body (`:59-60`) shows a docstring but no method overrides, leaving the write-method question from round 11's Implementability finding technically still open at the code-shown level.** `:59-60`: ```class RedactedTruthView(TruthStore):\n    """Same Protocol; results with split=held_out have item_ids/content stripped (aggregates pass)."""```. Because `TruthStore`'s own methods are written as `...`-bodied stubs in the `Protocol` block (`:52-57`), a class that inherits from `TruthStore` without overriding `open_work_unit`/`append_event`/`record_eval` would, read as literal Python, silently execute the inherited `...` body and return `None` rather than raising — the worst of the three options (no-op vs. raise vs. pass-through) discussed in round 11's Implementability finding is exactly the one a naive reading of this snippet defaults to. This is very likely not what is intended (§6.1's own lifecycle text states only "the §6 orchestrator" — a JUDGE-side component holding `bundles.judge` — ever calls these methods, and the §8 DI example shows the SOLVE-visible `Retriever` receiving only `bundles.solve` for reads, so the write methods are architecturally unreachable from SOLVE in the wiring as shown), but the class snippet itself does not say so, and "architecturally unreachable given the one example shown" is a weaker guarantee than "the type itself refuses". Scored as a residual, not a blocking correctness defect, because it was not among round 11's five required items and the surrounding prose (`:93,187`) makes the intended read (redacted-view-for-reads-only) clear enough for a careful implementer; it is flagged here so it does not silently recur as a "fresh instance" in a later round.

No other formula, inequality, or derived claim in §6.1/§6.2 changed this round beyond the two items above; the identity-hash formula (`:168-173`), the `open_work_unit`/`append_event`/`record_eval` three-field `AppendResult` contract (`:183,193,197`), and §6.2's `GraphDelta`/`MergeReport` schemas (`:213-222`) are unchanged from r11 and remain correct at the level established in rounds 2–7.

## Strongest adversarial objection

**Even with the two-bundle wiring fully shown and the self_modify read-capability check now explicit, the `RedactedTruthView`'s stated redaction rule — strip `item_ids`/content, pass aggregates (`n_pass`/`n_total`) through unchanged — does not bound how narrow a query can be before an "aggregate" becomes a de facto single-item signal, and neither document states or tests a floor on it.** `DATA-LAYER.md:187`: "aggregates like `n_pass/n_total` pass through: outcomes are not secrets, the items are." This is sound when an aggregate spans many items, but the eval-record granularity this document itself establishes is the **work unit** — "the work unit is the eval run (matching the batched `evals` row over `item_ids`)" (`:180`) — and nothing bounds how small a held-out sample a single work unit's `evals` row can cover. `ALGORITHM-v0.2-pathway-learner.md:82` (§4.1) describes `secret = suite[s].held_out @ rotating_sample` with no stated minimum sample size, and `retrieve()`'s truth modality (§16.4, `:421`) is queryable by the SOLVE-mutable retrieval config (§17.1, `:454`) on arbitrary filter criteria (`read_events(**filter)`, `DATA-LAYER.md:56`) — including, presumably, narrow filters on `skill`, `difficulty`, `checkpoint_id`, and `attempt_idx` that could in principle isolate a single work unit's `evals` row. If that row's `n_total` is small (say 1–3, plausible for a narrowly-scoped rotating sample), its `n_pass`/`n_total` aggregate *is* an item-level (or near-item-level) outcome signal even though `item_ids` themselves are stripped — reconstructing "this specific narrow slice of held-out items passed/failed" without ever seeing an `item_id`. Neither `DATA-LAYER.md` nor the cited ALGORITHM sections state a minimum aggregation granularity, a query-shape restriction on the redacted view (e.g., "no filter combination that could resolve to `n_total` below some floor `k_agg`"), or a test for this. This is a different failure mode from every prior round's finding in this chain (all of which concerned whether a mechanism *exists or is wired*, not whether an existing, correctly-wired mechanism has a *hole in its own definition of what counts as safe to pass through*), and it sits exactly on the P1 boundary (`ALGORITHM-v0.2-pathway-learner.md:8`, "make the measurement independent of the optimization") this section exists to protect — a SOLVE-side component that can reconstruct held-out outcome information at fine enough granularity can, in principle, feed it back into retrieval/decision heuristics it is allowed to edit (§17.1's SOLVE side includes "retrieval config," `:454`), reopening RC-2's memorization concern through the one channel this round's fix deliberately left open by design.
