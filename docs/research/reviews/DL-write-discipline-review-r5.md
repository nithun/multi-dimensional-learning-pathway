## Findings by dimension

### 1. Correctness

**The three round-4 blockers this round targeted are genuinely fixed** (schema, port method + record-class exemption, `AppendResult` contradiction — see closure table). This is real, independently-verifiable progress, not restated prose.

**A new, previously-latent correctness gap is exposed by the very mechanism that fixes round 4: `open_work_unit` mints identity with no dedup, no idempotency key, and no protection against being called more than once for a single real occurrence.** `DATA-LAYER.md:174` — "`attempt_idx` = the **persisted count** of prior rows for that `(episode, suite)` — never an in-memory counter." Every call to `open_work_unit(episode_id, suite_id)` succeeds and mints a *new*, valid `WorkUnit` with an incremented `attempt_idx` — there is no field, check, or return value (`WorkUnit{occurrence_id, attempt_idx}`, not `AppendResult`, so it has no `deduped` slot at all) by which the store can refuse or fold together two mint calls for what is, in reality, one genuine attempt. The whole section's over-counting guarantee — "a literal retry reuses the id... reads its id from the durable work-unit row" (`:175`) — is true *only if the caller already knows the id to read*. The document's own crash-recovery justification exposes exactly when a caller cannot know this: `:178` — "calling it after a crash simply opens attempt `n+1`, **correct because a crashed attempt's records never landed**." That final clause is an *assumption*, not a guarantee the store can verify: a caller that crashes (or times out) *after* a successful `record_eval` call but *before* it durably observes the acknowledgment cannot distinguish "my records never landed" from "my records landed but I didn't hear back," and — per the document's own stated recovery procedure — will call `open_work_unit` again, receive a fresh `attempt_idx = n+1`, redo (or resubmit) the work, and have **both** the original and the redo accepted as genuinely distinct, non-deduped occurrences (their `occurrence_provenance` tuples differ by `attempt_idx` alone), **both moving the posterior**. This is the identical class of failure round 1 found (double-counting) and round 2's adversarial pass named directly ("a retry harness that... gets a new id every time... silently double-counting into `(α,β)` again") — round 5 has closed the *reference*-side half of that objection (an invented occurrence is now rejected) but has not closed the *mint*-side half (a genuine, ordinary at-least-once-delivery ambiguity at the mint call itself still produces two valid, accepted occurrence ids for one real attempt). This is not a contrived scenario; it is the standard "did my write succeed" ambiguity of any networked write, applied to the one operation in this design that has no idempotency protection at all.

**Round-4 item 5 (the embedded-tier count-then-insert race) remains completely unaddressed** (see closure table) — this compounds the above finding, since a race on the "persisted count" derivation is a second, independent way for two concurrent `open_work_unit` calls for the same `(episode, suite)` to observe the same stale count and mint colliding `attempt_idx` values (a correctness bug distinct from, but adjacent to, the retry-ambiguity finding above).

**Minor secondary issue: `rejected_ingest`'s `payload_hash` cannot itself restore lost evidence.** `:180`'s claim that "rejected work's compute is not lost *evidence*... re-association preserves them" is true only insofar as the *caller* retains the original payload — the store's own truth log retains a hash, not the content, so if the caller does not independently persist the record client-side, the claim does not hold as stated. This is a real but narrower gap than the mint-side issue above.

## Strongest adversarial objection

**The document's own stated justification for its crash-recovery behavior is the precise location of a live, undetected double-counting risk, and no test in five rounds has ever targeted it.** `DATA-LAYER.md:178` says calling `open_work_unit` again after a crash "simply opens attempt `n+1`, correct because a crashed attempt's records never landed." This sentence is offered as a closing argument, but it is actually a conditional claim smuggled in as a fact: it is correct *if and only if* the caller can reliably know that its prior attempt's `record_eval`/`append_event` calls truly never landed. In any real distributed or even just crash-prone single-process system, a caller can lose its process *after* a write succeeds server-side but *before* it durably learns the write succeeded (the classic write-then-ack-loss ambiguity) — and the caller's only available recovery behavior, per this same document, is to call `open_work_unit` again and proceed as if starting fresh. When that happens, the "crashed" attempt's records did land, the new attempt's records also land, and both are individually well-formed, individually accepted (each is a "genuine" occurrence under a different `attempt_idx`), and both move the Beta posterior — a silent double-count, indistinguishable from a genuine second measurement, invisible to every test named across all five rounds of this gate (`test_occurrence_id_stable_across_restart` tests the *opposite* direction — that a restart does *not* cause a false dedup — but nothing tests that a restart *does not* cause a false new-count). This is not a new failure mode invented for this review: it is the *precise* over-counting risk round 1 found, round 2's adversarial pass named directly ("a retry harness that... gets a new id every time... silently double-counting"), and rounds 3–4 kept re-locating without ever closing — round 5 simply moved it one layer deeper, from "does the harness reuse ids" (now made moot by the reference check, which only validates that a referenced id exists, not that it's the *right* one) to "does the harness correctly know when it's allowed to mint a new one." Five rounds in, the mechanism that would make "correct because a crashed attempt's records never landed" actually true — an idempotency key on `open_work_unit`, a distributed-commit-style two-phase mint, or an explicit acceptance of this residual risk with a bound on its exposure — has never been specified.

## Verdict

**needs-revision**

Three of round 4's five items are genuinely and independently closed this round (a concrete `work_unit_opened` schema, the `open_work_unit` port method with a sound record-class exemption argument, and the fully cross-checked `AppendResult` three-field fix) — real, verifiable progress, and the first round since round 1 in which the recurring "stale canonical declaration" defect class does not reappear somewhere new. The score moved from round 4's 64 to 66 — a small net gain, because the round's own new mechanism (the full mint/record/enforce lifecycle) surfaces a fresh instance of exactly the failure mode this gate exists to close (mint-side double-counting under an ordinary write-ack-loss race), and round 4's fifth item (the embedded-tier count-then-insert race) was carried forward unaddressed rather than closed or explicitly deferred. Both CRITICAL dimensions Red-team resistance (66) is below 70; Correctness (72) and Safety (77) clear 70 but the aggregate remains well below 80.

1. **Give `open_work_unit` an idempotency mechanism, or explicitly bound/accept the residual risk.** State how a caller that is uncertain whether its prior `open_work_unit`/`record_eval` calls landed (crash or ack-loss, not just "the crashed attempt's records never landed") is prevented from minting a second, genuinely-accepted occurrence for one real attempt — e.g., a caller-supplied idempotency token checked at mint time, an explicit "is there an unresolved open work unit for this (episode, suite)?" query the caller must consult first, or a stated, bounded acceptance of the residual double-count risk with a test that measures its rate.
2. **Add a regression test for the mint-side double-count scenario** — the inverse of `test_occurrence_id_stable_across_restart`: that an ack-loss-then-retry at the `open_work_unit` call itself does not result in two accepted, posterior-moving occurrences for one real attempt.
3. **Close round 4's still-open item 5** — state explicitly whether the count-then-insert derivation of `attempt_idx` is race-safe under the embedded tier's concurrency model, or extend the §6.2 writer-lock discipline to cover `TruthStore.open_work_unit` too.
4. **State what the caller is expected to do if it no longer holds the original payload after a rejection** (`:180`) — the store retains only `payload_hash`; either state that a caller-side durability obligation exists (and how it's tested), or specify a mechanism by which the store itself could support recovery of the full payload.
5. **Consolidate the two test lists** (`:182` and `:221`) into one enumeration — this specific discoverability gap has now been flagged across three consecutive rounds (3, 4, 5) without being addressed.
